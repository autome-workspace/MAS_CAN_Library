# 動かないとき

| | |
|---|---|
| 読む人 | 主制御のプログラムを書く人 |
| 前提 | [はじめて回す](first-run.md) を読んだ |
| 読むとできること | モーターが回らない理由を、自分で絞れる |

## まず、これを書き込む

[はじめて回す](first-run.md) で作ったプロジェクトの `src/main.cpp` の中身を、[`examples/md_check/src/main.cpp`](../../../examples/md_check/src/main.cpp) の中身に置き換えて、書き込みます。`platformio.ini` は、そのままで構いません。シリアルモニタ（115200）を開きます。

`md_check` は、モーターを 1 つ回そうとしながら、**回らない理由を 1 語で表示する**例です。

```
offline  duty +0.00  fault 0x00000000
```

行の頭の言葉を見て、下の同じ名前の節を読んでください。

| 言葉 | 意味 |
|---|---|
| [`offline`](#offline) | 基板の声が届いていません |
| [`estop`](#estop) | 緊急停止がかかっています |
| [`wait`](#wait) | 基板との打ち合わせが済んでいません |
| [`mixed`](#mixed) | 指令の種類が混ざっています |
| [`fault`](#fault) | 基板が異常を知らせています |
| [`stopped`](#stopped) | 基板が止めています |
| [`ok`](#ok) | 指令は届き、基板は従っています |

相手の番号は、`md_check` の中の `can.md(0)` の 0 です。確かめたい基板の番号に合わせてください。

CAN_MD か micro-MD を 1 枚だけ使っているなら、`ok` の節まで読めば足ります。

この表示を出しているのは、`md_check` の中の `check()` という短い関数です。ライブラリの「確かめる関数」を、上から順に呼んでいるだけです。自分のプログラムが動かないときは、`check()` を写して使えます。

## `offline`

基板の声が、主制御に届いていません。次の順に確かめます。

1. **基板の電源。** CAN_MD と micro-MD は、番号が 0 だと LED が消えたままなので、LED だけでは判断できません。CAN_MD なら、DIP スイッチの 1 だけを ON にして電源を入れ直します。LED が 1 回ずつ点滅すれば、電源は来ていて、ファームも動いています。確かめたら、プログラムの番号も 1 に合わせるか、スイッチを戻します。
2. **トランシーバの電源と GND。** トランシーバにも電源が要ります。
3. **H と L。** 入れ替わっていると、どの基板とも話せません。基板の端子の、どちらが H かは [今ある基板](../boards.md) にあります。
4. **終端抵抗。** 線の両端の 2 か所に入っているかを見ます。
5. **基板の番号。** プログラムの番号と、基板の番号（ch）が合っているかを見ます。CAN_MD と micro-MD は、LED の点滅の回数が ch です。
6. **主制御のピン。** `platformio.ini` の `CAN_TX`、`CAN_RX` が、つないだピンと合っているか、入れ違っていないかを見ます。
7. **基板のファーム。** 前の版（v0）のファームが入った基板とは、話せません。入っている版を、主制御から確かめる方法は、今はありません。先輩に確かめるか、ファームを書き込み直します。書き込みの手順は、[今ある基板](../boards.md) から、各基板の資料にあります。

## `estop`

緊急停止がかかっています。**誰が、なぜかけたのかを確かめてから**、`can.clearEstop()` で解除します。値を毎回置いているプログラムは、解除するとすぐ動き出します。

緊急停止の間に主制御を書き込み直すと、基板だけが止まったまま残ります。このときも `estop` と出ます。

## `wait`

ライブラリが、基板との打ち合わせをしています。この間、ライブラリは「止まれ」を送ります。ふつうは 1 秒もかかりません。

ずっと続くときは、基板に何かを断られています。次の 2 か所をプログラムに足すと、断られたときに表示されます（[`examples/md_serial_test`](../../../examples/md_serial_test/src/main.cpp) の書き方です）。

```cpp
void onSettingError(mcan::Device &dev, uint8_t result) {
    Serial.printf("! MD %d setting failed (%d)\n", dev.ch(), result);
}
```

```cpp
can.onSettingError(onSettingError); // setup() の中で
```

`result` が 255 なら、基板から返事がありません。それ以外なら、基板が断っています。

## `mixed`

同じ 4 個の組で、指令の種類が混ざっています。0〜3 番、4〜7 番のように、4 個ずつが 1 組です。1 組の中で `setDuty`、`setCurrent`、`setSpeed` を混ぜると、番号のいちばん小さいものと同じ種類のものしか動きません。

種類の違うモーターを、別の組の番号にします。

## `fault`

基板が異常を知らせています。表示の `fault 0x...` の数字が、異常の中身です。

| 数字 | 意味 |
|---|---|
| `0x00000002` | 基板が覚えていた設定が壊れていたので、既定の値で起動しました |
| `0x00000004` | 通信が一度止まって、戻りました |
| `0x00000100` | 過電流 |
| `0x00000200` | 過熱 |
| `0x00000400` | 電源の電圧が低い |
| `0x00000800` | 電源の電圧が高すぎる |
| `0x00001000` | エンコーダの異常 |
| `0x00002000` | モーターのドライバの異常 |
| `0x80000000` | XDrive の中継機で、上のどれにも当てはまらない異常 |

2 つ以上が同時に起きると、数字は足し合わされます。`0x00000300` は、過電流と過熱の両方です。どの異常を知らせるかは、基板によります。

`motor.clearFault()` で消せます。原因が残っていれば、また立ちます。

## `stopped`

基板が、自分の判断でモーターを止めています。理由は 2 つ考えられます。

**その基板にできない指令を送っている。**
基板ごとに、こなせる指令が違います。`md_check` は `setDuty` を使います。

- XDrive の中継機に `setDuty` は使えません。`setSpeed` か `setCurrent` を使います。
- CAN_MD と micro-MD に `setSpeed` は使えません。
- CAN-Servo のモーターは `setDuty` だけです。

こなせる指令は、[今ある基板](../boards.md) の一覧にあります。

**指令が途切れている。**
基板は、指令が 0.1 秒届かないと止まります。自分のプログラムでこう出るなら、`can.update()` を `loop()` で毎回呼んでいるか、`loop()` の中に長い `delay()` が無いかを見ます。一瞬回って止まる、がくがく動く、というときも同じです。

## `ok`

指令は届いていて、基板は従っています。それでも回らないなら、次を見ます。

- **値が小さすぎる。** モーターは、ある強さを超えるまで動き出しません。`setDuty(0.3f)` を `0.5f` に上げて試します。
- **モーターの線、機構の引っかかり。**

## 行の右に、英語の文が出る

主制御の側で起きたことです。

| 文 | 意味 |
|---|---|
| `port start failed` | 線を始められませんでした。ピンの番号を確かめます |
| `command conflict` | 指令の種類が混ざっています。[`mixed`](#mixed) と同じです |
| `out of memory` | 主制御のメモリが足りません |
| `bus load high` | 線が混みすぎています |

## そのほかの症状

**主制御が再起動を繰り返す。**
H と L の入れ違いなど、配線の誤りで起きることがあります。線が異常なまま送ろうとすると、ESP32 の通信の部品が落ちるためです。

**緊急停止を解除したのに動かない。**
解除のとき、ライブラリは、置いてあった値を全部「止まれ」に戻します。ボタンを押した瞬間にだけ値を置くような書き方だと、置き直すまで動きません。

**電源を入れ直した後、しばらく動かない。**
基板は、起動してから 0.2 秒は動きません。その間に、ライブラリが打ち合わせをやり直します。プログラムは何もしなくてよく、済めば動き出します。

**逆に回る。**
`setDuty` や `setSpeed` の符号を逆にします。別の機体で使っていた基板が、「逆に回す」という設定を覚えていることもあります。今のライブラリには、この設定を読む関数がありません。

## ほかの基板

XDrive の中継機と、サーボの基板を使っている人のための節です。

**XDrive の中継機で回らない。**
[`stopped`](#stopped) と [`mixed`](#mixed) に加えて、次を確かめます。

- XDrive の側の事前の設定（校正、番号、通信の速さ）が済んでいて、中継機のファームの設定と合っているか。
- XDrive の電源を入れた直後ではないか。XDrive は、電源が入ってから 1 秒は回りません。
- 止まり方の種類。電源の瞬断や電圧の低下は、中継機が自分で直します。過電流や暴走は、`motor.clearFault()` を呼ぶか、緊急停止を解除するまで止まったままです。
- XDrive が 1 台だけ見えないなら、その XDrive の電源を入れ直します。

詳しくは [`firmware/xdrive-relay/README.md`](../../../firmware/xdrive-relay/README.md) にあります。

**サーボが動かない。**
サーボの基板は返事をしないので、基板の LED を見ます。

| LED | 考えられること |
|---|---|
| 消えている | 基板に電源が来ていません |
| 緑のまま | 主制御の指示が届いていません。線、終端抵抗、サーボの番号を確かめます |
| 青なのに動かない | 指示は届いています。サーボの電源、つないだ端子、`configCalibration` の値を確かめます |
| 赤 | 緊急停止がかかっています。理由を確かめてから、`can.clearEstop()` で解除します |

## 今は、プログラムから分からないこと

- 線の上に、どの番号の基板がいるか。一覧にする道具は、まだこのリポジトリにありません。
- 基板が止めている理由そのもの。`stopped` の 2 つの理由は、表示からは区別できません。
- 基板の種類と、ファームの版。
- 基板が覚えている設定の値（回転の向き、電流の上限など）。
- サーボの基板の様子。
- 過去に起きたこと。表示の右の文は、最後の 1 つだけです。

## それでも分からないとき

人に聞く前に、次の 2 つを控えておくと、話が早く進みます。

- `md_check` の表示。
- 基板の LED の様子。
