# 動かないとき

> **下書き（2026-11-15）。** 症状は、作者が部で実際に多かったと挙げたものを先に置いています。書いてある動きは、ライブラリと基板のコード、各基板の資料と突き合わせました。スキャナ（`examples/md_scan`）は、ビルドは確かめましたが、実機ではまだ動かしていません。

| | |
|---|---|
| 読む人 | 主制御のプログラムを書く人 |
| 前提 | [はじめて回す](first-run.md) を読んだ |
| 読むとできること | 症状から、原因の見当を付けられる。線に何がつながっているかを一覧で見られる |

## 最初に見る 3 つ

1. **基板の LED。** 点いているか、どう点滅しているかを見ます。意味は [今ある基板](../boards.md) にあります。CAN_MD と micro-MD は、ch が 0 のとき、ch を示す LED が消えたままです。消えているだけでは、故障とは限りません。
2. **シリアルの表示。** プログラムに、`motor.online()` と `motor.stopped()` を表示する行を入れます。[`examples/md_serial_test`](../../../examples/md_serial_test/src/main.cpp) が、そのまま使える例です。
3. **スキャナ。** 下の節のとおりです。

## スキャナで、線の上を一覧にする

[`examples/md_scan`](../../../examples/md_scan/) を主制御に書き込むと、線につながっているモーターの基板を、1 秒ごとに一覧にします。モーターは動かしません。

```
MD  0  current:yes speed:no   stopped
MD  1  current:yes speed:no   running
-- 2 MD, bus 3%, rx overflow 0
```

| 表示 | 意味 |
|---|---|
| `MD 0` | モーターの 0 番がいます |
| `current:yes` | 電流の指令（`setCurrent`）をこなせます |
| `speed:yes` | 速度の指令（`setSpeed`）をこなせます |
| `stopped` / `running` | 止めています / 指令に従っています（値が 0 の指令でも、こう出ます） |
| `E-STOP` | 緊急停止で止まっています |
| `FAULT 0x...` | 異常があります。後ろの数字が中身です |
| `checking...` | 見つけた直後です。次の表示を待ちます |
| `no MD found` | 1 枚も見つかりません |

使うときの注意:

- **ほかの主制御がつながっている線では使わないでください。** スキャナ自身が主制御として動き、基板の設定の一部を書き直すからです。ロボットのプログラムを止めてから使います。
- **サーボの基板は出ません。** サーボの基板は返事をしないためです。
- **duty をこなせるかは出ません。** XDrive の中継機は duty をこなせませんが、一覧からは分かりません。

## `offline` のまま、`MD not ready` と出る、スキャナに出ない

基板の声が、主制御に届いていません。次の順に確かめます。

1. **基板の電源。** 電源が来ているかを確かめます。CAN_MD と micro-MD は、ch が 0 だと ch の LED が消えたままなので、LED だけでは判断できません。
2. **H と L。** 入れ替わっていると、どの基板とも話せません。
3. **終端抵抗。** 線のいちばん端の 2 か所だけに入っているかを見ます。
4. **基板の番号。** プログラムの `can.md(0)` の番号と、基板の ch が合っているかを見ます。CAN_MD と micro-MD は、LED の点滅の回数が ch です。スキャナなら、何番にいるかがそのまま出ます。
5. **主制御のピン。** `platformio.ini` の `CAN_TX`、`CAN_RX` が、実際につないだピンと合っているかを見ます。TX と RX が入れ違っていないかも見ます。

## 主制御が再起動を繰り返す

ESP32 が、起動しては落ちることを繰り返す場合です。H と L の入れ違いなど、配線の誤りで起きることがあります。線が異常な状態のまま送ろうとすると、ESP32 の通信の部品が落ちるためです。配線を直すと収まります。

## `online` なのに回らない

基板とは話せています。多い順に並べます。

**その基板にできない指令を送っている。**
基板ごとに、こなせる指令が違います。できない指令を受けた基板は、安全のために止まります。このとき `motor.stopped()` が `true` です。

- XDrive の中継機に `setDuty` は使えません。最小の例（`md_minimal`）は `setDuty` なので、そのままでは回りません。`setSpeed` か `setCurrent` を使います。
- CAN_MD と micro-MD に `setSpeed` は使えません。
- CAN-Servo のモーターは `setDuty` だけです。

こなせる指令は、[今ある基板](../boards.md) の一覧か、スキャナの `current` と `speed` の欄で分かります。

**値が小さすぎる。**
モーターは、ある強さを超えるまで動き出しません。`setDuty(0.1f)` で回らなければ、`0.5f` まで上げて試します。

**`update()` が呼ばれていない、間隔が長い。**
`can.update()` を `loop()` で毎回呼んでいるか、`loop()` の中に長い `delay()` が無いかを見ます。基板は、指令が 0.1 秒届かないと止まります。一瞬回って止まる、がくがく動く、というときも、まずここを疑います。

**同じ 4 個の組で、指令の種類が混ざっている。**
0〜3 番、4〜7 番のように、4 個ずつが 1 組です。1 組の中で `setDuty`、`setCurrent`、`setSpeed` を混ぜると、番号のいちばん小さいものと同じ種類のものしか動きません。`motor.commandConflict()` が `true` なら、これです。種類の違うモーターは、別の組の番号にします。

**緊急停止がかかっている。**
`motor.estopLatched()` が `true` なら、緊急停止で止まっています。**誰が、なぜかけたのかを確かめてから**、`can.clearEstop()` で解除します。毎回値を置いているプログラムは、解除するとすぐ動き出します。

**異常がある。**
`motor.hasFault()` が `true` なら、基板が異常を知らせています。中身は `motor.faultDetail()` で読めます。`motor.clearFault()` で消します。原因が残っていれば、また立ちます。

**準備が終わらない。**
`motor.ready()` が `false` のままなら、ライブラリが基板との打ち合わせを終えられていません。その間、ライブラリは「止まれ」を送り続けます。`can.onSettingError(関数)` を入れておくと、基板に何を断られたかが分かります。

## 緊急停止を解除したのに動かない

解除のとき、ライブラリは、置いてあった値を全部「止まれ」に戻します。解除した瞬間に、前の値で動き出さないようにするためです。

`loop()` の中で毎回値を置いているなら、次の周から動きます。ボタンを押した瞬間にだけ値を置くような書き方だと、解除の後に置き直すまで動きません。

緊急停止の間に主制御を書き込み直したり、再起動したりした場合は、基板だけが止まったまま残ります。`motor.estopLatched()` が `true` なら、`can.clearEstop()` を呼びます。

## 電源を入れ直した後、しばらく動かない

基板は、起動してから 0.2 秒は動きません。その間に、ライブラリが基板との打ち合わせをやり直します。プログラムは何もしなくてよく、済めば、置いてある値で動き出します。

位置（`motor.position()`）を使っているなら、基板が止まっていた間にモーターが動いた分は数えられていません。原点を合わせ直します。

## 逆に回る

`setDuty` や `setSpeed` の符号を逆にします。

別の機体で使っていた基板が、「逆に回す」という設定を覚えていることもあります。今のライブラリには、この設定を読んだり書いたりする関数がありません。プログラムの側で符号を合わせてください。

## XDrive の中継機で回らない

上の「できない指令」「指令の種類が混ざっている」に加えて、次を確かめます。

- **XDrive の側の事前の設定。** PC から、校正、番号、通信の速さを入れてあるか。中継機のファームの設定と合っているか。
- **XDrive の電源を入れた直後ではないか。** XDrive は、電源が入ってから 1 秒は回りません。
- **止まり方の種類。** 電源の瞬断や電圧の低下で止まったときは、中継機が自分で直して回り出します。過電流や暴走などで止まったときは、`motor.clearFault()` を呼ぶか、緊急停止を解除するまで止まったままです。`motor.hasFault()` で分かります。
- **XDrive が 1 台だけ見えない。** 線を抜き差しした後などに起きます。その XDrive の電源を入れ直します。

詳しい動きは [`firmware/xdrive-relay/README.md`](../../../firmware/xdrive-relay/README.md) にあります。

## サーボが動かない

サーボの基板は返事をしないので、プログラムからは確かめられません。基板の LED を見ます。

| LED | 考えられること |
|---|---|
| 消えている | 基板に電源が来ていません |
| 緑のまま | 主制御の指示が届いていません。線、終端抵抗、サーボの番号を確かめます |
| 青なのに動かない | 指示は届いています。サーボの電源、つないだ端子、`configCalibration` の値を確かめます |
| 赤 | 緊急停止がかかっています。理由を確かめてから、`can.clearEstop()` で解除します |

サーボの番号は、基板にファームを書き込むときに決まります。何も変えていない基板は、J2 の端子が 0 番です。

## それでも分からないとき

人に聞く前に、次の 3 つを控えておくと、話が早く進みます。

- シリアルの表示（`online`、`stopped`、`estopLatched`、`hasFault` と `faultDetail` の値）。
- 基板の LED の様子。
- スキャナの一覧。
