# 確かめ方

| | |
|---|---|
| 読む人 | 基板のファームを作る人 |
| 前提 | ファームが書き込めて、基板が CAN の線につながっている。[守ること](rules.md) を読んだ |
| 読むとできること | 主制御のプログラムを自分で書かずに、作った基板が決まりどおり動くかを確かめられる |

確かめ方は 2 段あります。先に PC の上で、次に実機で確かめます。

## PC の上で確かめる

基板が無くても、ライブラリの基板側（node）の動きは PC で確かめられます。

```sh
make -C lib/mas/test
```

4 つのテストが走り、それぞれ `all ... tests passed` と出れば成功です。ライブラリを触っていなければ、ここは通るはずです。

| テスト | 確かめること |
|---|---|
| `test_node` | node だけ。偽のフラッシュを使い、起動と FB、指令、緊急停止、設定、起動の猶予、保護、duty を出せない基板を確かめます |
| `test_roundtrip` | 主制御のライブラリと node を 1 つのプログラムでつなぎ、やりとりを確かめます |
| `test_core`、`test_host` | 線の上のフレームの形と、主制御のライブラリ |

自分のファームの中の判断（番号が範囲の外のときの扱いなど）を PC で確かめたいときは、その部分をハードウェアに触らない関数に分けて、node と一緒にコンパイルします。

```sh
gcc -std=c11 -I lib/mas/include my_test.c \
    lib/mas/src/can/node.c lib/mas/src/can/core/md_frame.c lib/mas/src/can/core/setting.c
```

書き方の見本は [`lib/mas/test/test_node.c`](../../../lib/mas/test/test_node.c) です。

## 実機で確かめる

主制御にするマイコン（ESP32 か Raspberry Pi Pico）が 1 つ要ります。プログラムは書かなくて構いません。用意してある例を書き込んで使います。

線には、確かめたい基板と主制御だけをつなぎます。モーターは、回っても危なくないようにしておきます。

### 1. 見えるかを確かめる

[`examples/md_serial_test`](../../../examples/md_serial_test/) を主制御に書き込み、シリアルモニタ（115200）を開きます。この例は、シリアルから 1 行ずつ命令を送って、基板を試す道具です。最初は 0 番の基板を見ています。自分の基板が別の番号なら、`ch 3` のように送って切り替えます。

状態は、0.2 秒ごとに 1 行で出ます。

```
[3] on  0.000 A duty +0.00 stop fault 0x0
```

確かめること:

- [ ] `on` と出る。`--` のままなら、主制御に声が届いていません。[動かないとき](../host/troubleshooting.md) の「`offline`」を見ます。基板の側では、通信の速さ、`mas_can_node_ready()` を呼んでいるか、を疑います。
- [ ] `on` の後ろの `(wait)` が、すぐ消える。消えないなら、設定への返事ができていません。
- [ ] `stop` と出ている。指令を送っていないので、止まっているのが正しい動きです。

### 2. 動かして確かめる

同じ例のまま、命令を送ります。

| 命令 | すること |
|---|---|
| `ch 3` | 相手を 3 番にする |
| `d 0.3` | duty 0.3 で回す |
| `i 0.5` | 電流 0.5 A で回す |
| `s` | 止める |
| `e` / `c` | 緊急停止 / 解除 |
| `x` | 異常を消す |

確かめること:

- [ ] `d 0.3` で回る。`d -0.3` で逆に回る。`s` で止まる。
- [ ] 回している最中に、CAN の線を抜く。**0.1 秒ほどで、モーターが止まる。** 線を戻すと、また回る。
- [ ] `e` で止まる。表示に `estop` と出る。この間、`d 0.3` を送っても回らない。
- [ ] `c` で解除する。解除しただけでは回らない。もう一度 `d 0.3` を送ると回る。
- [ ] 回している最中に、基板の電源を入れ直す。何もしなくても、また回り出す。
- [ ] 電流を測れない基板に `i 0.5` を送る。回らず、表示に `stop` と出る。できない指令で止まるのが、正しい動きです。
- [ ] 表示の電流や duty が、実際の動きと合っている。

サーボの基板は、[`examples/servo_minimal`](../../../examples/servo_minimal/) で確かめます。サーボは返事をしないので、動きと LED を目で見ます。指令の線を抜いて、サーボの力が抜けることを確かめます。

### モーターが 2 個以上の基板

モーターごとに ch が違うので、`ch` で相手を切り替えて、1 個ずつ確かめます。スイッチの値が 3 で、モーター 2 個の基板なら、ch は 6 と 7 です（決め方は [雛形から始める](start.md#モーターが複数のときの番号)）。

1. `ch 6` を送ります。表示が `[6] on` になれば、1 個目のモーターの声が届いています。
2. `d 0.3` を送ります。**1 個目のモーターだけ**が回ることを確かめます。2 個目も回るなら、ファームの中で、モーターの番号とピンの対応がずれています。
3. `ch 7` を送ります。例は、切り替える前の相手（ch 6）に止める値（duty 0）を送るので、1 個目のモーターは止まります。表示が `[7] on` になることを確かめます。
4. `d 0.3` を送り、2 個目のモーターだけが回ることを確かめます。
5. 上の「確かめること」のうち、線を抜く、緊急停止、電源の入れ直しを、ch 7 のままでもう一度確かめます。
6. 受け持たない ch（この基板なら `ch 5` と `ch 8`）に切り替えて、`--` のままになることを確かめます。`on` になるなら、ほかの基板がつながっているか、この基板が受け持つ ch を取り違えています。
7. スイッチで番号を決める基板なら、スイッチの値を変えて電源を入れ直し、受け持つ ch が変わることを確かめます。スイッチの値が 0 のときと、最大のときは、必ず試します。

### 3. 基板の情報を読む

基板の種類の番号やファームの版が正しく返るかは、今の主制御のライブラリからは読めません。USB-CAN のアダプタで、線に直接フレームを送って確かめます。

#### 基板の情報を生のフレームで読む

ch 0 の MD に、項目 1（基板の種類）を読む例です。要求は ID `0x400`、応答は ID `0x408` で、どちらも data は 8 byte です。

| | ID | data（16 進） |
|---|---|---|
| 要求 | `0x400` | `00 00 01 00 00 00 00 01`（ch 0、読む、項目 1、値 0、通し番号 1） |
| 応答 | `0x408` | `00 00 01 00 03 00 01 01`（結果 0、値 `0x00030001`。micro-MD、版 1） |

- **byte 0 が ch です。** ch 6 の基板に送るなら、要求の data は `06 00 01 00 00 00 00 01` になります。
- **応答の byte 3〜6 が値です。** 上の 2 byte が基板の種類、下の 2 byte が版です。雛形のまま（`MAS_CAN_BOARD_RESERVED`、版 1）なら、値は `0x00000001` で、応答の data は `00 00 01 00 00 00 01 01` です。
- **項目 2 を読むと、ファームの版が返ります。** 要求の byte 2 を `02` にします。
- **項目 0 を読むと、応答の data 8 byte がすべて固有 ID になります。** この応答には、ch も通し番号も入りません。
- **受け持たない ch に送ると、何も返りません。** 返らないときは、byte 0 の ch を確かめてください。

項目と値の形の全体は、仕様書の [settings.md](../../spec/settings.md) にあります。

## 最後に

[守ること](rules.md) の点検表を、上から順にもう一度見ます。実機で確かめにくい項目（フラッシュに書いている間の出力、番号が範囲の外のとき）は、その場面をわざと作って確かめます。
