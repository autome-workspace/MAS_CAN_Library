# コントローラの仕様（v0.2）

状態: **合意**（2026-10-01）。残りは、ボタン番号の対応表と、文字を分割して送る共通の形（後で決める）。

## 前提（ユーザ、2026-10-01）

- 標準的なゲームパッドに合わせる: 左スティック（x, y）、右スティック（x, y）、ボタン 8 個、トリガー 2 種。
- 文字の送信にも対応したい。
- 向きはコントローラ（の受信基板）→ 主制御。送る周期は送り手が決める。
- 帯 3（通常の周期データ）。ID はコントローラ 1 台（ch）ごとに 1 つ。

## 状態のフレーム（DLC 8）

| byte | 内容 |
|---|---|
| 0 | 左スティック x（int8、−127〜+127、右が正） |
| 1 | 左スティック y（int8、上が正） |
| 2 | 右スティック x（int8） |
| 3 | 右スティック y（int8） |
| 4 | トリガー L2（アナログ、uint8、0〜255） |
| 5 | トリガー R2（アナログ、uint8、0〜255） |
| 6–7 | ボタンと状態（16 bit、下の表） |

| bit | 内容 |
|---|---|
| 0–7 | ボタン 8 個（押している ＝ 1） |
| 8–11 | 十字キー（上、右、下、左） |
| 12 | **つながっている**（無線のリンクが生きている） |
| 13 | 基板に異常あり（全種類で共通の意味） |
| 14 | 肩のボタン L1 |
| 15 | 肩のボタン R1 |

- スティックとトリガーは 8 bit にした。人の操作には十分な分解能で、8 byte にちょうど収まる。
- bit 12 が大事。無線が切れたとき、受信基板は最後の値を送り続けてはいけない。bit 12 を 0 にし、スティックとトリガーを 0、ボタンを全部離した状態にして送る。
- ボタンの番号とゲームパッドの実際のボタン（A、B、L1 など）の対応表は、別に決める。

**判断 1（2026-10-01）: 案 B。** 「トリガー 2 種」は、肩のボタン（L1、R1）とアナログのトリガー（L2、R2）。L1 と R1 は、予約だった bit 14–15 に入れる。これで 8 byte をちょうど使い切る（ユーザ）。

## 送るタイミング

- 変化したらすぐ送る。変化がなくても一定の周期（例えば 50 Hz）で送る。
- 主制御は、このフレームが届かないこと（例えば 200 ms）でも、コントローラの異常を知れる。

## 文字の送信

**判断 2（2026-10-01）: 双方向。** コントローラ → 主制御（コマンドの入力など）と、主制御 → コントローラ（画面への表示など）の両方に対応する。

どの向きでも、形は同じにできる:
- 文字列は UTF-8 で送る。長さは可変なので、複数のフレームに分ける。
- 各フレームの先頭 1 byte に、通し番号と「最後のフレーム」の印を入れる。残りの 7 byte が文字。
- 文字のフレームは、状態のフレームとは別の ID にする。コントローラ 1 台につき、上りと下りで 2 つ。
- 文字は急がないので、優先度は低くてよい（自作フレームの帯の近く）。

データを複数のフレームに分けて送る仕組みは、ToF と個別のやりとりでも要る。できれば共通の形にしたい（後で決める）。
