# 主制御のライブラリの API（検討中）

状態: **検討中**（2026-10-04 開始）。使う側のたたき台 [examples/api_tour/src/main.cpp](../../examples/api_tour/src/main.cpp)（ESP32-S3、ATA6561。API をひととおり使う例）を書きながら決める。ライブラリの 2 層の構成は [requirements.md](requirements.md) の D3・D4。

- 置き場所は当面このリポジトリの `lib/`。ハードウェアに依存する層としない層を分ける。部の mas libraries に後で移す可能性がある（[md-firmware-draft.md](md-firmware-draft.md) §3）。

## 決まったこと

| # | 点 | 決定 | 日付 |
|---|---|---|---|
| A1 | 相手の指し方 | **バスから取っ手をもらう形**: `mas::can::Md w = can.md(ch);`。取っ手は軽く（どのバスの何番の ch かだけを持つ）、中身（指令の値、FB）はバスが持つ。同じ ch の取っ手が何個あっても食い違わない。`w.ch()` で番号を読める。**名前は階層で分ける**（ユーザ）: `mas::can::Bus`、`mas::can::Md`、`mas::can::Controller`、ヘッダは `<mas/can.h>`、置き場所は `lib/mas/`（PlatformIO のライブラリ「mas」。将来の `mas/core` などと並ぶ）。C で書く部分は接頭辞 `mas_can_`。~~`mas::CanBus`~~（I2C や SPI のバスと分けるために一度そうしたが、相手の型（Md、Tof など）もバスごとに分ける必要があるので階層にした）。長ければ `namespace mcan = mas::can;` で別名を付ける | 2026-10-04 |
| A2 | 単位 | **API に出る値は全部 SI**（ユーザ）。速度 rad/s、電流 A、設定の電流の上限 A・最高速度 rad/s・最大加速度 rad/s²、PID ゲインも SI（ライブラリが換算して書く）、速度の分解能は rad/s/LSB。プロトコル（仕様書、DBC）は rpm と mA のままで、換算はライブラリの中に隠す。**float の物理量が基本**で、生の整数は上級者向けに別名で出す（`setSpeedRaw(int16_t)` など）。**位置は積み上げたカウントの int64 だけ**（1 回転 ＝ 65536、電源投入時が 0）。double の rad は出さない（ユーザ）。rad への換算は小さな関数で添える。引き換え: 監視（DBC）で見える数字とコードの数字が一致しない（10 rad/s ≈ 95.5 rpm） | 2026-10-04 |
| A3 | 送受信のタイミング | **アプリが `can.update()` を呼ぶ形を基本にする**（ユーザ）。理由: 主制御は ESP32 だけとは限らない（ユーザ）。ライブラリはハードウェアと RTOS に依存しない作りにし、時間を進めるのはアプリ。`update()` の中で、受けたフレームの振り分け、期限の来た周期送信（指令 100 Hz、SYNC 20 Hz）、再起動の後始末を行う。コールバックも `update()` の中から呼ぶので、`loop()` と同じ流れで動き、排他は要らない。`loop()` が止まれば送信も止まり、基板は途絶判定（100 ms）で止まる（安全側）。そのため「アプリが呼ばなければ止める」仕組みは要らない。`loop()` は少なくとも約 20 Hz 以上で回す必要がある（説明書に書く）。CAN の送受信（ESP32 なら TWAI）と時刻は、移植の層（ポート）としてライブラリの下に分ける。ESP32 で裏のタスクに任せたい人向けの補助は、後で足せる | 2026-10-04 |
| A4 | 保存しない設定 | (1) ライブラリは、アプリが書いた保存しない設定（MD なら電流と速度の分解能 48、49）を覚え、基板の再起動（起動の知らせ、異常の詳細の bit 0）に気づいたら自動で送り直す。電源投入の直後も同じ流れ。(2) 再起動に気づいてから、設定の応答で書けたと確かめるまでは、その ch に止める値だけを送る（分解能が食い違ったまま動き出すのを防ぐ）。アプリからは `w.ready()` が false の間として見える。(3) 設定を書く関数は待たずに戻る。送信と応答の確認は `update()` の中で 1 つずつ進める。書けなかったときは A7 の異常の知らせと同じ道で伝える | 2026-10-04 |
| A6 | コントローラの値 | (1) スティックは −1.0〜+1.0（値 ÷ 127）、トリガーは 0.0〜1.0 の float。生の値は別名（`leftXRaw()` など）。(2) ボタンは `held(b)`（押されている）、`pressed(b)`（前回の `update()` から今回までに押された瞬間があった）、`released(b)`（離された瞬間があった）。瞬間は届いたフレームを全部見て記録し、短い押下を取りこぼさない。名前は位置で付ける: 十字キー `Up` `Down` `Left` `Right`、右側のボタン `North` `South` `West` `East`、`L1` `R1` `L3` `R3`。(3) 200 ms フレームが来なければ `connected()` を false にし、スティックを 0、ボタンを離した状態にする（受信基板が落ちた場合の受け皿）。(4) デッドゾーンは既定では無し。`pad.setDeadzone(0.05f)` で選べる | 2026-10-04 |
| A7 | 異常 | (1) 問い合わせ（`w.hasFault()`、`w.faultDetail()`）とコールバック（`can.onFault(...)`。`update()` の中から、新しく立った bit だけを渡す）の両方を用意する。ライブラリは FB の bit 0 が立ったら異常の詳細を 1 回読んで置いておく。基板と話せないことは `w.online()`、設定のやりとりの失敗は同じ知らせの道で伝える。(2) 再起動の bit 0 だけはライブラリが消し、それ以外の bit はアプリが `w.clearFault()` を呼んだときに消す（勝手に消すと、続いている異常で知らせが繰り返され、アプリが気づく前に消えるため） | 2026-10-04 |
| A8 | E-stop と解除 | (1) **自分で `can.estop()` を呼んだ主制御だけが、`clearEstop()` を呼ぶまで E-stop を 10 Hz で送り続ける**（後から起動した基板もラッチされる。spec-draft.md の Q32 を解決）。(2) E-stop の間は、アプリの指令の代わりに止める値を送る。解除するときは、アプリの指令も止める値に戻す（D21）。(3) **ほかの送り手から受けた E-stop は見るだけで、送り直さない**（伝染してループし、復帰できなくなるのを防ぐ。ユーザの指摘）。`can.estopped()` は true になり、誰かの解除（`0x001`）を受けたら終わる。止めた人が解除するまで止まり続ける（ほかの人の解除で覆らない）。(4) 解除は 1 回送り、100 ms 後も FB の bit 5（ラッチ中）が立っている基板があれば、最大 3 回まで送り直す。それでも残れば異常と同じ道で知らせる | 2026-10-04 |
| A11 | FB をまとめて読む | **`w.feedback()` が `const Md::Feedback &`（参照）を返す**（UdonLibrary の調査から。ユーザ）。中身は電流、速度、位置、duty、状態の byte、最後に受けた時刻、online と、状態の bit を読む関数。コピーしないので個別のゲッタと同じ軽さ。中身が書き換わるのは `update()` の中だけ（A3）なので、loop の 1 回の中では値がそろったまま変わらない。`update()` をまたいで比べたいときはコピーして取っておく。**個別のゲッタ（`w.speed()` など）も残す**（同じものを見る） | 2026-10-05 |

### A1 の補足: メモリ

- 取っ手は「バスへのポインタ ＋ ch の番号」で 8 byte 程度。
- 中身はバスが種類ごとの最大の ch 数だけ持つ。MD 32 ch に、指令の値、FB、受けた時刻、保存しない設定（単位）、状態をまとめて 1 ch 60 byte 程度として約 2 KB。サーボ 64 ch、汎用 I/O、コントローラ、ToF などを全部足しても 10 KB 程度の見込み。ESP32-S3 の RAM（512 KB）に対して問題にならない。
- 基板のファーム（F042、RAM 6 KB）は、このライブラリではなく基板側のコアを使い、自分が受け持つ ch の分だけを持つので、影響しない。
- 使わない種類の分まで持つのが気になるなら、最初に使ったときに確保する形にもできる（後で決めればよい）。
