## 3. 決定した設計の断片

| # | 内容 |
|---|---|
| D1 | 短絡ブレーキは専用の group や指令にしない。duty の指令の中に、PWM オフ時の減衰モード（ブレーキ／空転）を選ぶ 1 bit を持たせる。duty 0 とブレーキの組み合わせが短絡ブレーキになる |
| D3 | ライブラリを 2 層に分ける。下の層は、フレームの組み立てと解読だけを行う純粋な関数で、送信のタイミングは持たない。上の層は、送信の予定を管理して周期送信とレート制限を行う。アプリにタイミングを任せる使い方は、下の層を直接使う（上の層の `update()` をアプリの loop から呼ぶ形でもよい）。この使い方ではレート制限は効かない。ただし、送り忘れても基板が途絶判定で止まるので、安全は保たれる（ユーザの要望、2026-09-29） |
| D4 | 下の層は「契約を満たす API」として公開する。利用者が自作したフレームも、同じ形で登録すればライブラリの周期送信に乗せられる |
| D5 | 周期は提案した案で合意（モーターへの指令 100 Hz、FB 100 Hz、サーボ 50 Hz、ToF はセンサの測定周期）。ただしコントローラは「コントローラ → 主制御」の向きに送るので、周期は送り手のコントローラ基板が決める。性質はセンサや FB と同じになる |
| D2 | duty の分解能は、16 bit から 1 bit をモード指定に使っても足りる（STM32G4 で 20 kHz の PWM を出しても約 8500 段階） |

## 4. ToF の要件

- マトリクス型（VL53L8CX）は 8×8 と 4×4 を選べるようにする。1 行だけを選んで送れるようにする（実績では 1 行 8 点だけを使っていた）。
- 送る項目:
  - **必須**: 距離、target_status、nb_target
    - nb_target は、基板側で「ターゲット無しなら状態を 255 にする」処理を済ませれば、送らずに済む。
  - **残す**: sigma
  - **診断用のビルドだけ**: signal、ambient など
  - target_status は 1 つの信頼度にまとめない。棄却理由を区別する必要がある。
- 測定した時刻のタイムスタンプを扱う必要がある（実績の実装では持っていた）。§4.7 の同期した時刻を載せる。
- 開始・リセット・設定変更が要る。これは実質的に許可制と同じ問題なので、できるだけ単純に作り、必要ならファームウェアに持たせる。
- 実績（F3RC_2026 の R2 機体）:
  - L8CX は 8×8 区画、10 Hz、SPI 接続。
  - L1X は Short モード、測定時間 20 ms、ROI 16×4。
  - 根拠: `~/dev/Eugene_Ramirez/archive/F3RC_2026/dev/tof_vl53l8cx/docs/capabilities.md:94-121`、`main/R2/docs/facts.md:134-140`、`main/R2/docs/decisions.md:554-567`

## 4.5 追加の要件（2026-09-29）

- **C610 をこの体系の一員として扱いたい。**
  - C610 の ID は固定なので、変えられない。指令は `0x200`（ESC 1〜4）と `0x1FF`（ESC 5〜8）、FB は `0x201`〜`0x208`。
  - 指令は 1 フレームに 4 台分をまとめて送る形式なので、ライブラリはまとめて送る処理を必ず持つことになる。
  - v0 の電流 group 0（`0x200` と FB の `0x201`〜`0x204`）は、C610 と同じ ID になっている。
  - DLC が 8 未満の指令を C610 が受け付けるかは**未確認**。マニュアルは 8 byte と定めているだけ。C610 宛てのフレームは常に DLC 8 で送ることにして、この問題を回避する。自作の基板は、短い DLC も受け付ける。
- **方向性（合意）**: 番号は ch に振り、4 台分をまとめて送る（C610 と同じ形）。v0 で起きた基板どうしの影響は、規則で塞ぐ（ブレーキ専用の group をやめる、使っていない slot の値の意味を決める、同じフレームに入る ch の種類をそろえる）。
- **同じ 4 ch の組では、指令の種類を混ぜない（規則）**。そのため、使っていない slot には 0（＝止める）を入れる（案 1）。「指令なし」を表す値は不要。
- **位置の指令は、duty と同じく割合で表す**。実際の範囲（例えば昇降機構の高さ）は、基板の設定に持たせる。制御対象の自由度が高すぎるので、単位を仕様で決めないため（P5 の対象外に当たる）。
- **電流の単位は 2 mA/LSB（±65.5 A）**（2026-10-01 に 10 mA/LSB から変更。指令と FB の両方）。電流制御で実際に指令したい範囲は、足回りで 10〜20 A、大きなモーターで 30〜40 A 程度と見積もった。10 mA/LSB（±327 A）では範囲が大きすぎたため、需要に 1.5 倍の余裕を持たせる形に絞った。C610 は別の API で扱うので、この単位には影響しない。
- **1ch の基板と 4ch の基板が同じ種類として混在する**（例: CAN_MD は 1ch、CAN-Servo のモーター部は 4ch）。以前から対応させるつもりだった。
  - 案: 番号を**基板ではなく ch（モーター）に振る**。基板は、連続した ch をまとめて持つ入れ物として扱う。

## 4.6 ch の一般化と通信の型（提案中、2026-09-29）

- ch を「(種類, 番号)」に一般化する。例: モーター ch 5、サーボ ch 3、ToF ch 2、コントローラ ch 1。
- 基板は、ch をまとめて持つ入れ物として扱う。1 枚の基板が複数の種類の ch を持ってもよい（例: CAN-Servo は サーボ 8 ch とモーター 4 ch）。
- 通信は次の 3 つの型に分けられる。ID の空間は、この型ごとに割り振ることを検討する。

| 型 | 向き | 内容 | 形 | 例 |
|---|---|---|---|---|
| 1. 周期指令 | 主制御 → 基板 | 状態を周期的に送る | 4 ch（または 8 ch）分をまとめて 1 フレーム | モーター、サーボ、エアー |
| 2. 周期データ | 基板 → 主制御 | 送り手が決めた周期で送る | 1 ch に 1 本。1 回分のデータが大きければ複数本に分ける | モーターの FB、ToF、コントローラ |
| 3. 個別のやりとり | 双方向 | たまにしか起きない。問い合わせと応答 | 相手の ch を指定する | 設定、開始やリセット、種類と版の問い合わせ |

- 優先度は、型の順に固定しない。周期データの中でも、ToF のように時刻のずれが問題になるものは優先度を高くしたい（ユーザ、2026-09-29）。
  - 注: 優先度で縮められるのは、バスの調停で待つ時間だけ（負荷が中程度なら 1 ms 未満）。時刻の精度は、§4.7 の時計の同期で確保する。

- **基板と ch の関係（合意、2026-09-29）**: ch は種類ごとの列ベクトルで、基板はそのベクトルの連続した範囲にまたがる入れ物。複数の種類のベクトルにまたがってもよい。基板専用の周期フレームは持たない（基板ごとに ID を消費するため）。
  - 生存の確認は、ch ごとの FB で代用する。
  - 基板全体の異常は、FB の状態 byte の 1 bit で知らせる。詳しい中身は 3 つ目の型（個別のやりとり）で問い合わせる。
  - 基板を識別する仕組みは、3 つ目の型の中にだけ持たせる。
  - FB を持たない基板（サーボ、エアー）の生存確認が要るかは疑問（ユーザ）。3 つ目の型そのものは、設定値を送るため（中継役の上限、ToF の解像度と行の選択、開始やリセット）に必要。

- **基板の識別（方向性、2026-09-29）**: 案 (b) を採る。基板番号を別に振ると、DIP は ch の設定に使われているので、実質的にファームウェアの書き換えが必要になるため（ユーザ）。
  - DIP で決めるのは「主な種類の先頭の ch」だけ。
  - 他の種類の ch の範囲は、基板の種類ごとに決まった規則で計算する。この規則は基板の性質なので、ファームウェアが持つ（P5 の対象外）。
  - 3 つ目の型で使う基板の識別も、「主な種類と DIP の値」から計算する。旧プロトコルの group と同じ発想で、それを整理し直した形。

- **処理の置き場所の原則（合意、2026-09-30）**: 基板が持つのは、「細かい時間分解能が要る処理」（チャタリング除去、変化した時刻の記録、速度ループなど）と、「そのハードウェアに固有の処理」（ToF の状態値の後処理など）だけにする。判断や意味づけ（逆運動学、飽和、入力の意味）は主制御が持つ。設定値の扱いは P9 に従う（ファームウェアの既定値 → フラッシュ → 主制御からの上書き）。

## 4.7 時系列が重要なデータの扱い（検討中、2026-09-29）

知りたいのは「受け取った時刻」ではなく「測定した時刻」。この 2 つの差（遅延）と、遅延のばらつき（ジッタ）が問題になる。

遅延は次の各段階で積み重なる。

| 段階 | 目安 |
|---|---|
| 測定そのもの（積分の時間幅） | ToF で 20 ms 以上。値はその中点の時刻のものと考える |
| 基板の処理ループ | 数 ms。ループの作り方しだい |
| 送信待ち（バスの調停） | 負荷が中程度なら 1 ms 未満 |
| 送信 | 1 本あたり約 0.13 ms。分割したデータ（ToF の 8×8 区画は 32 本）なら数 ms |
| 主制御の受信処理 | 1 ms 未満〜数 ms |

時刻の求め方は 3 案ある。

| 案 | 仕組み | 誤差 | 手間 |
|---|---|---|---|
| A. 受信した時刻で代用する | 主制御が受け取ったときに時刻を記録する | 遅延の全部（数 ms〜10 ms） | 何も要らない |
| B. 経過時間を載せる | 基板が「測定の中点から送信までの µs」を載せる。主制御は受信時刻からそれを引く | 1 ms 未満 | 1〜2 byte |
| C. 時計を同期する | 主制御が同期フレームを定期的に送り、基板は同期した時刻を載せる | µs 級 | 同期の仕組みが必要 |

**方針（ユーザ、2026-09-29）: C（時計の同期）を採用する方向。** どうせ MAS CAN に載せるなら同期しておけばよく、データのフレームも時刻の載せ方が一つにそろって整理される。

C の骨子（案）:
- 主制御が同期フレーム（SYNC）を定期的に送る。中身は主制御の時刻（µs）。ID は E-stop の次に高い優先度にする。
- 基板は、SYNC を受信した瞬間の自分の時計との差を記録し、主制御の時刻に換算する。
- 時刻が必要なデータには、2 byte の時刻の欄を載せる（~~当初は下位 16 bit~~ → 同期の印 1 bit と、下位 15 bit の µs に変更。下の「時刻の仕様」を参照）。分割して送るデータは、先頭の 1 本に時刻を載せる。
- 精度は 1 ms を十分下回る見込み。主な誤差は、SYNC が送信待ちになる時間と、ESP32 側の処理の遅れ。さらに精度が必要になったら、送信が終わった時刻を後から追って送る 2 段階の方式に広げられる。
- 注意点が 2 つある。
  - ~~基板のクロックは水晶が前提~~ → 水晶以外にセラロック（セラミック発振子）の基板もある（ユーザ、2026-09-29）。
    - 時刻の同期は、周波数のずれも SYNC から推定して補正すればよい（PTP や NTP と同じ考え方で、ずれの量と速さの両方を合わせる）。
    - ただし **CAN の通信そのもの**が発振子の誤差に耐えられるかは、別に確かめる必要がある。1 Mbps でセラロック（±0.5% 程度）を使うと、SJW を大きく取れば収まる見込み。ただし SJW=1（今の CAN_MD の設定）では許容範囲（約 0.3%）を超える可能性がある。
  - SYNC は、主制御が生きていることを示す合図も兼ねられる。

**時刻の仕様（合意、2026-09-30）**:

| 項目 | 内容 |
|---|---|
| SYNC の中身 | 主制御の起動からの経過時間。32 bit、µs（約 71 分で一周） |
| 同期する前の扱い | 「同期していない」印を付ける |
| データに載せる時刻の欄（**共通形式**、2026-09-30） | 2 byte。bit 15 ＝ 同期している（時刻が有効）、bit 0–14 ＝ 同期した時刻の下位 15 bit（µs、約 32.8 ms で一周）。同期の印を時刻の欄に入れるのはユーザの提案 |
| 時刻から元の値へ戻せる条件 | 遅延が約 32 ms 未満であること。データの時刻は必ず受信時刻より過去なので、主制御は「受信時刻から過去側に戻す」一方向の計算で元に戻す。そのため、一周（32.8 ms）の全体を使える |
| SYNC が途絶えたとき | 補正を続けたまま時刻を出す。数秒途絶えたら「同期していない」扱いにする |
| SYNC による途絶判定 | **使う**（ユーザ）。下を参照 |

- **SYNC を途絶判定にも使う**（ユーザ、2026-09-30）:
  - ~~SYNC の周期は 50 Hz、途絶判定は 100 ms~~ → **SYNC は 20 Hz、SYNC の途絶判定は 250 ms**（4 回続けて落ちても耐えられる）で決定（2026-09-30）。SYNC の途絶判定は予備の手段で、素早く止めるのは ch ごとの指令の途絶判定（100 ms）の役目なので、長くしても差し支えない。時刻の同期も、10〜20 Hz あれば回帰で十分に推定できる。
  - ch ごとの指令の途絶判定（100 ms）も残す。担当を分けた複数の主制御がある場合、SYNC を送るのはそのうち 1 台（時刻の親）だけなので、他の主制御が落ちたことは SYNC では分からないため。
  - SYNC が途絶えたときの動作は、指令が途絶えたときと同じ（出力を止める。ラッチしない）。
- **SYNC は必須にする（ユーザの提案、2026-09-30）**。バス全体で共有する仕組みで、使うかどうかは選ばせない。存在することのデメリットはほぼ無い（20 Hz で負荷は約 0.3%）。
  - 選べるのは、ライブラリが**自動で送る**か（既定）、アプリが**手動で送る**か（高度な使い方。D3）だけ。
  - 指令を送るものは、主制御でも PC のデバッグツールでも、必ず SYNC を送る。
  - 基板の規則:
    - 最初の SYNC を受け取るまでは、SYNC の途絶判定は働かない。時刻には「同期していない」印を付ける。
    - 最初の SYNC を受け取ってからは、SYNC の途絶判定を有効にしたままにする（電源を切るまで）。
  - 時刻の要るセンサのフレームには、時刻の欄を常に設ける。同期していない間は、印で区別する。印は、まだ同期していない場合と、同期が落ちた場合（SYNC の途絶判定に達した場合）の両方で付ける（例えばデジタル入力は、1 byte のうち使っていない上位 4 bit の 1 つを使う）。
  - SYNC を送るとき、送信キューが空くのを待つ時間には上限（例えば 5 ms）を設ける。上限を過ぎたら、そのまま送る。キューが空かない原因は、バスの異常（ACK を返す相手が無い、bus-off）か、アプリが送信キューを埋め続けることのどちらか。
- **主制御側のジッタ**（2026-09-30）: SYNC に載せた時刻と、実際にバスに出た時刻の差がジッタになる。主な原因は、ESP32 の送信キューで他のフレームの後ろに並ぶこと（最大で数 ms）。対策は次のとおり。
  1. SYNC は、送信キューが空になった瞬間に時刻を取って送る（空でなければ少し待って確かめ直す）。他のフレームを止めたり、順番を入れ替えたりはしない。旧ドライバは、キューが空なら `twai_transmit` の中でその場でハードウェアに書くので、待つのは調停の最大 1 本分（約 0.13 ms）だけになる。アプリが自分の判断で SYNC を送れる API も用意する（D3 と両立させるため）。
  2. 基板は、何回分もの SYNC から回帰でずれを推定するので、ランダムなジッタは平均される。一定の遅れは全基板に共通なので、基板どうしの時刻の比較には影響しない。
  - 送信完了の通知で、どのフレームが完了したかを区別できるか: 旧ドライバの通知（alert）にはフレームの情報が無い。ただし ESP32 の TWAI は送信バッファが 1 つで、キューの順に送るので、順番を数えれば特定はできる（壊れやすい）。新しいドライバのコールバックには、完了したフレームの情報が付く見込み（**要確認**）。確実なのは self-reception で、戻ってきたフレームの ID（`0x002`）で SYNC だと分かる。
  - **開発環境の制約**: 開発は PlatformIO の Arduino フレームワークで行う。PlatformIO 公式の espressif32 プラットフォームは、長く arduino-esp32 2.x（ESP-IDF 4.4 系）のままで、3.x（ESP-IDF 5 系）を使うにはコミュニティ版の pioarduino が要る、という事情がある（バージョンは**要確認**）。**決定（2026-09-30）: 対象は PlatformIO 公式のプラットフォーム（arduino-esp32 2.x 系）とする。** pioarduino は品質上は使えるが、利用者に求めることが増え、既存のライブラリとの互換性の問題も出るため採らない。ライブラリは旧ドライバ（`driver/twai.h`）を前提にする（pioarduino でも動く）。旧ドライバには受信の割り込みコールバックが無く、受信時刻はタスクがキューから取り出した時点になる。そのため、3 は当面の対象外とし、1 と 2 で 1 ms 未満の精度を目指す。
  3. さらに精度が要る場合は、2 段階の方式にする。送信が完了した瞬間の時刻を割り込みで取り、後続のフレームで送る。新しい ESP-IDF の TWAI ドライバには、送信完了の割り込みコールバックがある見込み（**要確認**）。自分の送ったフレームを自分で受信する機能（self-reception）で時刻を取る方法もある。

誤差の影響の目安: 2 m/s で走っていると 1 ms で 2 mm、180°/s で回っていると 1 ms で 0.18° ずれる。

## 4.8 足回りのバス分割（検討中、2026-09-29）

- バスの帯域を大きく使う足回りの MD を、RP2040 の PIO CAN（can2040）を使って**別のバスに分ける**構想がある。RoboMaster の FB の量が多いため。
  - 目安: C610 の FB は 1 kHz で出る。4 台で約 4000 本/秒になり、それだけでバスの約半分を使う。
- RP2040 が中継役となり、下の足回りバスと上の主バスをつなぐ。どこまで制御ループを中継役の中で閉じるか、主バスに何を送るかは、R2 の実装をもとに検討した（下の「合意した構成」）。
- R2 の実績（根拠: `F3RC_2026/main/R2/docs/decisions.md:1208-1318`、`src/domain/drive/wheel_loop.hpp`、`docs/can.md`）:
  - 足回りは M2006 と C610 が 4 台、オムニ 4 輪を X 字に配置していた。ESP32-S3 から C610 に直結し、同じバスを制御盤とアームも共有していた。
  - ループはすべて S3 の中で 100 Hz で回していた。流れは「車体速度（vx, vy, ω）→ 逆運動学 → 飽和の処理（倍率 k を返す）→ 輪ごとの PID と FF → 電流」。500 Hz に分ける案は宿題のまま。
  - 経路追従と足回りのループの境目は、「車体速度を渡し、飽和倍率 k を返してもらう」1 か所だけだった。
  - オドメトリは駆動輪を使わず、AMT103 の測定輪 2 つ（S3 の PCNT で計数）と IMU で計算していた。
  - モーターの FB で使っていたのは rpm だけ（PID、スリップの推定、テレメトリに使用）。角度は使っていなかった。
  - バスの負荷は典型で 46%、最悪で 57% と見積もっていた（C610 の FB だけで 54%）。受信 FIFO があふれる問題があり、他の基板のフレームが埋もれていた。S3 には TWAI が 1 本しかなく SPI も使い切っていたので、分割は不可能と結論していた。RP2040 の中継案は過去にあったが、削除されていた。
- **切り分けの候補**: 境目を R2 と同じ「車体速度を渡し、飽和倍率 k を返す」にする。中継役の中で逆運動学と輪ごとの PID を回し、1 kHz まで上げることもできる。主バスに流れるのは、指令 1 本と FB 1〜2 本（各 100 Hz）程度になり、4000 本/秒から数百本/秒に減る。オドメトリは主制御に直結のままなので、中継役から送る必要はない。
- **合意した構成（2026-09-29）**: 主制御が逆運動学と飽和の計算（静的な上限）までを行い、各輪の目標速度を送る。中継役は各輪の速度ループ（最大 1 kHz）だけを受け持つ。主バスから見ると、中継役は「速度制御ができる 4 ch のモータードライバー」になるので、足回り専用の種類は要らない。電流制御で使う場合は、FB のレートが下がるだけになる。動的な限界（電流の上限、電池の電圧低下）は、FB の目標との差や状態として見える。
- **モーターの FB の標準形式の候補**（1 ch 1 フレーム、8 byte）: 速度 2 byte、電流 2 byte、状態 1 byte、位置 3 byte。
  - 位置は折り返すカウンタとし、主制御は前回との差を取って使う。スリップの検知に使う（100 Hz の速度を積分するより正確）。**単位は出力軸 1 回転 ＝ 65536 カウントで、3 byte**（256 回転で一周。ギア無しの高速な BLDC や、フレームが抜けた場合にも余裕がある）。決定。
  - 中継役が必要になるのは、固定の独自プロトコルで FB がうるさい機器（DJI）を使うときだけ。MAS CAN に直接つながる自作の MD は、FB のレートを設定できて速度ループも自分で持つので、中継は要らない。
  - 時刻は載せない（需要なし）。
  - 状態には、下のバスで C610 からの応答が途絶えたこと、電流の上限に当たったこと、下のバスのエラーなどを入れる。
  - R2 の実装は、現時点での到達点にすぎない。それ以上を想定して決める（ユーザ）。
- 仕様への影響:
  - 中継役は、主バスから見れば 1 枚の基板（速度制御の 4 ch MD）になる。足回り専用の ch の種類は要らない（上の「合意した構成」で解決）。
  - RP2040 で扱えるバスの本数: ユーザには、can2040 と PIO エンコーダを 1 つのブロックに同居させた実績がある。そのため、1 ブロックに 2 本載り、最大 4 本まで行ける可能性がある（未確認）。CAN-Servo のコメントには「can2040 は 4 つのステートマシンをすべて使う」とあり、実績と食い違う。実際の制約は、命令メモリと、1 Mbps の割り込みによる CPU の負荷になりそう。
  - **膨らみそうな論点（保留）**: 高度な制御で必要な性能を把握するには、実際に流れた電流などのデータが要る。機体の特性を主制御と中継役のどちらで把握し、どこまで簡略化するかの問題。案として、制御に要るデータは周期的に送り、分析用のデータ（輪ごとの電流など）は設定で有効にするか、間引いて送る。ToF の「診断用のビルドだけ」と同じ扱いにする。
