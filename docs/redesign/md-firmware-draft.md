# MD のファームウェアの構成（草案 v0.1）

状態: **草案**（2026-10-03 作成）。**§4 の API は案で、ユーザが見てから確定する**（ユーザ: API を決めるときは自分の目も入れたい）。それ以外は Claude に任されている。
プロトコルは [spec-draft.md](spec-draft.md)、MD の決定は [requirements.md](requirements.md) の D9〜D35。

## 1. 対象の基板と、今のファームウェア

### 基板（`~/Downloads/2ch-MD/`。シルクは「CAN-MD v1.1.0」）

| 項目 | 中身 |
|---|---|
| MCU | STM32F042F6P6（Cortex-M0、フラッシュ 32 KB、RAM 6 KB、FPU なし） |
| 発振子 | 16 MHz のセラミック発振子（PF0/PF1） |
| ch | **1 ch**（名前は 2ch だが、2 ch の予定が 1 ch になった） |
| 駆動 | DRV8701P ＋ ディスクリートの MOSFET。IN1/IN2 ＝ PA1/PA0（TIM2）。**空転は出せない**（nSLEEP 固定）。空転を求められたらブレーキに丸める（基板の都合。プロトコルは変えない） |
| 電流 | 5 mΩ ＋ DRV8701 のアンプ（20 V/V）→ PA6（ADC_IN6）。片方向で、駆動している間だけ測れる。DRV8701 の電流チョッピングの閾値 VREF を PA7（TIM3_CH2 の PWM ＋ RC）で与える |
| エンコーダ | **無い** → FB の bit 1 を立て、速度・位置の指令は「こなせない指令」で止める（D10） |
| 基板の位置 | DIP 3 bit（PA4、PB1、PA5。ON で 0、内部プルアップ）→ k ＝ 0〜7、ch ＝ k |
| LED | PB8（BOOT0 と兼用）の 1 個 |
| デバッグ | STDC14（SWD）、USART2（ST-LINK の仮想 COM） |
| 測れないもの | 電源電圧、温度、ドライバのフォルト（異常の詳細の bit 8〜13 は立てない） |

### 今の `firmware/CAN_MD`（旧プロトコル v0 で動いた実績あり）

- CubeMX で作った CMake のプロジェクト。ピンの割り当ては上の基板と同じ。**初期化（`MX_*_Init`）は土台にする**。
- **クロックは HSI（内蔵の RC 発振、8 MHz）× 4 ÷ 2 ＝ 16 MHz。** `.ioc` では PF0/PF1 を HSE 用にしているが、PLL の入力は HSI のままで、**基板のセラミック発振子は使われていない**。HSI の精度は工場出荷で ±1% 程度なので、D7（発振子の誤差の目安 ±0.5%）を満たさない。→ §5.1 で HSE に切り替える。
- CAN は 16 tq（BS1 11、BS2 4）、サンプル点 75%、SJW 1。→ D7 に合わせて直す。
- 電流の指令は、DRV8701 の**ハードウェアの電流チョッピング**で実現している（VREF を電流に見合う電圧にし、向きの側を常時オン）。電流の上限は 2.4 A（基板の連続定格を見た控えめな値）に固定。
- 電流の測定は、ADC を 64 回読んだ**最大値**（ブレーキで減衰している間は SO が無効なため）。
- PWM は TIM2、周期 533 カウント（16 MHz で約 30 kHz）。

## 2. 層の分け方

```
┌──────────────────────────────────────────────┐
│ コア（lib/mascan/。純粋な C。HAL も CAN の型も知らない）           │
│  共通: フレームの組み立てと解読、class 0、途絶判定、設定の枠組み、 │
│        共通の項目 0〜6、起動の知らせ、異常の詳細                  │
│  MD:   指令の解読、ch の状態、FB の組み立て、MD の設定項目、       │
│        （速度ループなどの計算。この基板では使わない）              │
├──────────────────────────────────────────────┤
│ ポート（firmware/CAN_MD/App/。F042 と、この回路に依存する）         │
│  CAN の送受信（bxCAN）、時刻、フラッシュ、固有 ID、DIP、LED、       │
│  モーターの出力（TIM2、TIM3）、電流の測定（ADC）                    │
├──────────────────────────────────────────────┤
│ CubeMX が書き出す初期化（Core/、Drivers/）。手で書き換えない        │
└──────────────────────────────────────────────┘
```

- コアは「入力を受けて、状態を変え、出力を返す」関数の集まりにする。コアが時計やハードウェアに触ることはない。時刻は引数でもらう。
- コアは PC でもコンパイルでき、テストを PC で回せる（§7）。
- コアのうち、フレームの組み立てと解読の部分は、主制御のライブラリの下の層（D3）とも共有できる形にする。
- 動的なメモリ確保（`malloc`）は使わない。RAM 6 KB に収める。

## 4. コアの API（**案。ユーザの確認待ち**）

### 4.1 フレーム

```c
typedef struct {
    uint16_t id;        // 11 bit
    uint8_t  dlc;       // 0〜8
    bool     rtr;       // リモートフレームか（D35: 0x000 以外は無視する）
    uint8_t  data[8];
} mas_frame_t;
```

### 4.2 基板側のコア（共通）

```c
// 起動時に 1 回。基板の性質（種類、受け持つ ch、固有 ID、版）と、種類ごとの部品を渡す
void mas_node_init(mas_node_t *node, const mas_node_config_t *cfg);

// フレームを 1 本受けたら呼ぶ（割り込みではなく、main のループから）
void mas_node_on_frame(mas_node_t *node, const mas_frame_t *f, uint32_t now_us);

// main のループから頻繁に呼ぶ。途絶判定、FB の送る時刻の管理など
void mas_node_tick(mas_node_t *node, uint32_t now_us);

// 送るフレームを 1 本取り出す。無ければ false。ポートが CAN に渡す
bool mas_node_pop_tx(mas_node_t *node, mas_frame_t *out);
```

- コアは送るフレームを自分の中の待ち行列に積むだけで、CAN には触らない。ポートが `pop_tx` で取り出して送る。
- 起動の知らせは、`mas_node_init` の後、ポートが「設定に応答できる状態になった」と伝えたときに積む（D30）。

### 4.3 MD の部分

コアが「何を出すべきか」を決め、ポートがそれをハードウェアに出す。ポートは測った値をコアに渡す。

```c
typedef enum {
    MAS_MD_OUT_STOP,     // 止める（止め方は brake で示す）
    MAS_MD_OUT_DUTY,     // duty（±16383 ＝ ±100%）
    MAS_MD_OUT_CURRENT,  // 電流（mA）
    MAS_MD_OUT_SPEED,    // 速度（rpm）。エンコーダのある基板だけ
} mas_md_out_mode_t;

typedef struct {
    mas_md_out_mode_t mode;
    bool    brake;       // 止めるとき、duty のオフの間: ブレーキか
    float   value;       // 単位は mode による（物理の単位）
    bool    reset_ctrl;  // 制御の状態をリセットすべきか（D21、D23）
} mas_md_output_t;

typedef struct {
    bool  current_valid;  float current_ma;
    bool  speed_valid;    float speed_rpm;
    bool  position_valid; uint32_t position;   // 24 bit
    int16_t duty_now;     // 実際に出している duty（FB の空いた欄に入れる）
    bool  current_limited;// 電流の上限に当たっている
    bool  protecting;     // 基板の保護で止めている（D18）
} mas_md_measure_t;

const mas_md_output_t *mas_md_output(const mas_node_t *node, uint8_t local_ch);
void mas_md_set_measure(mas_node_t *node, uint8_t local_ch, const mas_md_measure_t *m);
```

- 単位の換算（設定 48、49 による LSB）、飽和（D17）、止める値・途絶・E-stop の扱い、FB の状態の byte はすべてコアの中で行う。ポートは物理の単位（mA、rpm）だけを扱う。
- この基板には速度・位置が無いので、コアは `config` で「速度と位置は測れない」と知っていて、速度・位置の指令が来たら `STOP` を出す（D10）。

### 4.4 設定の項目の表

```c
typedef struct {
    uint8_t  number;      // 項目の番号
    uint8_t  type;        // INT32 / UINT32 / FLOAT32
    uint8_t  access;      // RW / RO / COMMAND
    bool     savable;     // 保存できるか（P10）
    // 値の確かめ（D19）と、書いたときの反映は関数で渡す
} mas_setting_def_t;
```

- 共通の項目 0〜6 と MD の項目 32〜49 はコアが持つ。基板固有の項目（128〜255）は、ポートが表を足せる。
- 「能力を超える値を抑える」（D19）の上限は、ポートが `config` で渡す（この基板なら電流の上限、FB の周期の上限など）。

### 4.5 ポートがコアに渡すもの（`mas_node_config_t` の中身）

| 中身 | この基板では |
|---|---|
| 種類と、受け持つ ch の範囲 | MD、先頭 ch ＝ k、数 1 |
| 固有 ID（64 bit） | F042 の 96 bit を D22 で畳む |
| 基板の種類と版、ファームの版、プロトコルの版 | `0x0001`、版 1、未定（Q14） |
| 測れるもの | 電流だけ |
| 能力の上限 | 電流の上限（ハードウェア）、FB の周期の上限 |
| 保存した設定を読む・書く関数 | フラッシュの最後のページ（§5.5） |
| 再起動する関数 | `NVIC_SystemReset()` |

## 5. この基板のポート（F042）

### 5.1 クロック（CubeMX で直す）

- **HSE（16 MHz のセラミック発振子）÷ 2 × 5 ＝ 40 MHz** に変える（今は HSI × 4 ÷ 2 ＝ 16 MHz）。
- 40 MHz にするのは、CAN のサンプル点をちょうど 80% にするため（48 MHz では 1 bit を 5 の倍数の tq に割れない）。
- フラッシュの待ち（latency）は 1 にする（24 MHz を超えるため）。
- 発振子の品番の精度は確かめる（D7 の目安 ±0.5%）。

### 5.2 CAN（D7）

| 項目 | 値 |
|---|---|
| プリスケーラ | 2（40 MHz ÷ 2 ＝ 20 MHz、1 tq ＝ 50 ns） |
| 1 bit | 20 tq ＝ 1（同期）＋ BS1 15 ＋ BS2 4 |
| サンプル点 | 16 / 20 ＝ **80%** |
| SJW | **4**（取れる最大） |
| 自動バスオフ復帰 | 有効（D32） |
| 自動再送 | 有効 |

受信のフィルタ（ハードウェアで絞る）:
- class 0: `0x000`、`0x001`、`0x002`（`0x002` は MD では時刻を使わないが、途絶判定に要る）
- class 2: 自分の ch が入る MD の指令のフレーム 4 本（`0x210 + f`、`0x218 + f`、`0x220 + f`、`0x228 + f`、f ＝ ch ÷ 4）
- class 4: `0x400`（MD の設定の要求）

### 5.3 モーターの出力

- **duty:** TIM2 の PWM で IN1/IN2 を出す。40 MHz では周期 1333 カウントで約 30 kHz（今と同じ周波数）。
- **電流:** 今のファームと同じく、DRV8701 のハードウェアの電流チョッピングを使う（VREF ＝ 電流に見合う電圧、向きの側を常時オン）。
  - 注意: VREF の RC（10 kΩ・1 µF）の時定数が 10 ms あるので、電流の指令を変えてから効くまで 10〜30 ms かかる。
- **止める:** 空転は出せないので、IN1 ＝ IN2 ＝ 1（ブレーキ）。
- **電流の上限（設定 33）:** 今のファームの 2.4 A は、基板の連続定格を見た控えめな値。焼いた値と、能力の上限（D19 の「抑える」値）をいくつにするかは、基板を作った方に確かめる。

### 5.4 電流の測定

- 今のファームと同じく、ブレーキで減衰している間は SO が無効なので、駆動している間の値を取る。
- 改善案: TIM2 の更新で ADC を起動し（ハードウェアのトリガ）、駆動している間の決まった位置で読む。ソフトで 64 回読んで最大値を取る今の方法より、CPU を使わず、値も安定する。最初は今の方法のまま動かし、後で入れ替える。
- 向きは、測った値ではなく出している向きで付ける（片方向の測定のため）。

### 5.5 設定の保存（フラッシュ）

- フラッシュの**最後のページ（1 KB、`0x08007C00`）**を設定の領域にする。リンカスクリプトで、プログラムがそこに入らないようにする。
- 中身: 見出し（印、形式の版、長さ）＋ 保存できる項目の値 ＋ CRC。CRC が合わなければ、焼いた値で起動し、異常の詳細の bit 1 を立てる。
- 書いている間（ページの消去に 20〜40 ms）は CPU が止まる。PWM はハードウェアなので出続けるが、CAN の受信の FIFO（3 本）があふれうる。仕様上は主制御の責任（A3.2）。

### 5.6 そのほか

- **固有 ID:** `UID_BASE`（`0x1FFFF7AC`）の 3 語を D22 で畳む。
- **DIP:** 起動時に 1 回読む（D33）。3 bit なので範囲外は起きない。
  - **重みは印字の番号で決める: 印字 1 ＝ bit 0、印字 2 ＝ bit 1、印字 3 ＝ bit 2**（2026-10-05、ユーザ）。全部 off で k ＝ 0（ch 0）。
  - ピンとの対応（2026-10-05 に実機で確かめた）: **印字 1 ＝ PA5、印字 2 ＝ PB1、印字 3 ＝ PA4**。on で GND に落ちる（内部プルアップ、読んだ値が 0 なら on）。
  - 回路図では DIP の 1 ＝ PA4、3 ＝ PA5 になっていて、印字と左右逆。旧ファームは回路図どおりに PA4 を bit 0 として読んでいた（印字 3 だけ on で 1）。回路図かフットプリントのピンの割り当ての食い違いと思われる。基板を作った方に伝える。
- **LED:** 動作の様子を示す（点滅の決め方は後で）。今のファームの「基板の番号の回数だけ点滅」を、k ＋ 1 回に変えて残す案がある。
- **オプションバイト:** BOOT0 のピンにプルダウンが無いので、オプションバイトで BOOT0 のピンを無視する設定（`nBOOT_SEL`）にするのが安全。書き込みのときに一度だけ行う。

### 5.7 大きさの見積もり（2026-10-04 に今のファームをビルドして測った）

| ビルド | フラッシュ | RAM |
|---|---|---|
| Debug（-O0） | 20,020 B / 32 KB（61%） | 2,000 B / 6 KB |
| Release（-Os） | 11,196 B / 32 KB（34%） | 2,000 B / 6 KB |

- 設定の領域に最後の 1 KB を取るので、プログラムに使えるのは 31 KB。
- 新しいファームは、設定の枠組みと float（FPU が無いのでソフトウェアの計算。ライブラリで数 KB）が増える。Debug でも収まるかは、コアを書いた段階で測る。収まらなければ、Debug でも最適化を `-Og` にする。

## 6. main のループと割り込み

```
割り込み: CAN の受信 → 受けたフレームを、リングバッファに積むだけ（コアは呼ばない）
main:
  初期化（CubeMX）→ DIP、固有 ID → 保存した設定を読む → mas_node_init
  → ポートの準備ができたら起動の知らせ（D30）
  ループ:
    リングバッファから取り出して mas_node_on_frame
    mas_node_tick(now)
    mas_md_output を見て、モーターの出力を更新
    電流を測って mas_md_set_measure
    mas_node_pop_tx で取り出したフレームを、CAN の送信の箱が空いていれば送る
```

- コアを割り込みから呼ばないのは、コアの状態を 1 か所（main）からしか触らないようにして、排他を考えずに済ませるため。
- 時刻は 1 ms の SysTick（`HAL_GetTick()` × 1000）で足りる（MD は時刻を FB に載せない）。

## 7. PC でのテスト

- `lib/mascan/test/` に、コアを PC の gcc でビルドして回すテストを置く。
- 例: 「E-stop → 解除 → 次の指令で動く」（D21）、「DLC を縮めた指令で自分の slot が外なら受けていない扱い」（D9）、「途絶 100 ms で止まる」、「設定の書き込みの範囲外は 3、能力を超える値は抑える」（D19）、「初期化は保存しない項目に触らない」（D29）。
- 時刻を引数で渡すので、100 ms の途絶も一瞬で試せる。

## 9. 確かめること

| # | 中身 |
|---|---|
| F1 | セラミック発振子の品番と精度（D7 の目安 ±0.5%） |
| F2 | 電流の上限（設定 33）の焼いた値と、能力の上限。今の 2.4 A の根拠 |
| F3 | DRV8701P の真理値表（空転が出せないこと）と、SO の電圧が PA6 の許容を超えないか |
| F4 | 手元の ST-LINK の種類 |
| F5 | 主制御の代わりに PC から CAN を送る手段（USB-CAN アダプタの有無） |
| F7 | **旧ファームの電流の指令は、ほぼ電流を制御できていない**（2026-10-05、実機で確認）。1 mA の指令で FB が約 600 mA、1 mA とは思えない速さで回る。原因の見込み: DRV8701 の打ち切り（チョッピング）に任せて向きの側を常時オンにしているため、ブランキングの間に 12 V がかかり、短絡ブレーキの遅い減衰と釣り合うところまで電流が上がる。VREF の刻みも約 62 mA と粗く、FB は ADC の最大値。**新しいファームでは、duty の PWM ＋ オンの区間の中で ADC を取る ＋ PI 制御のソフトの電流ループにし、DRV8701 の打ち切りは上限の保険にする**案。後で詰める |
| F6 | 配布: ほかの人が簡単に焼けるように、PlatformIO のプロジェクトにする案がある（ユーザ、2026-10-03）。**今回は ST の純正の環境で進める**。コアを `lib/` に分けておけば、後で PlatformIO 側から同じコアを使える |
