# 現行（v0）仕様の調査結果

2026-09-29 に調べた時点の内容。
仕様書は `firmware/CAN-Servo/main.md`（バス全体）と `firmware/CAN_MD/protocol.md`（CAN_MD 専用の版）の 2 本。

## 骨組み（設計判断）

| # | 判断 | 得ているもの | 代償 |
|---|---|---|---|
| A | 通常の CAN（FD ではない）、1 Mbps、11 bit ID | どの MCU でも使える | 1 フレーム 8 byte まで |
| B | ID を class(3) / group(5) / node(3) に分ける | ID を見れば用途がわかる | ID の空間が機能の数で固定される |
| C | 1 フレームに 4 台分の指令を詰める（サーボとエアーは 8 ch 分） | バスの負荷が小さい | 同じ group の基板どうしが影響し合う |
| D | 指令の種類を group で区別する | 中身を 1 台 2 byte にできる | モード切替が暗黙的になる |
| E | 許可無しで稼働し、100 ms 途絶で停止する | 単純 | 抜き差しの直後に動き出す |
| F | E-stop はラッチし、`"clr"` で解除する | 止め損ないにくい | 送るのは 1 回だけで、届いたか確かめられない |
| G | 基板番号を DIP で設定し、そこから group と node を計算する | 基板ごとの書き込みが要らない | 番号の重複を検出できない |
| H | FB は電流→速度→位置の順に積み、DLC で量を示す | 後から量を足せる | 状態やエラーを返す場所が無い |
| I | 単位は mA、rpm、duty（int16 全域）、サーボは 10 µs 刻み | わかりやすい | 位置の単位が未定 |
| J | 設定・診断・基板の検出をする手段が無い | 実装が軽い | 基板の版やエラーを知れない |

## 対応している台数

| 種類 | 仕様の上限 | 実際に使える数 |
|---|---|---|
| DC モーター（電流） | 16 | 8（CAN_MD。DIP が 3 bit のため） |
| DC モーター（速度・位置） | 16 ずつ | 0 |
| DC モーター（duty） | 16 | 16（CAN-Servo 1 枚に 4 台 × 4 枚） |
| 短絡ブレーキ | 16 | 0（group の割り当てがずれている） |
| サーボ | 32 ch | 32 ch（CAN-Servo 1 枚に 8 ch × 4 枚。枚数を増やすにはビルドし直しが必要） |
| エアー | 32 ch | 0 |
| IMU | 4 | 0（BNO055 の出力と同じ形式） |
| コントローラ | 4 | 0（ボタン番号の表の画像がリポジトリに無い） |

## ライブラリ（`lib/MotorCAN`）の問題点

1. **duty と短絡ブレーキの group が CAN_MD と逆**。
   - ライブラリと CAN-Servo: duty は 12〜15、ブレーキは 16〜19。
   - CAN_MD: この 2 つが逆。
2. **モードを切り替えると、前のモードの古い値が送られ続ける**（`MotorCAN.cpp:87-91`, `:305-308`）。
3. **同じ group の 4 台は、実質的に同じモードでしか使えない**。
   - 使っていない slot も値 0 として送るため、CAN_MD はブレーキ group の 0 を「解除」と受け取り、同じ group の他の基板を止めてしまう。
4. 細かい問題:
   - `DriveMode` の値の範囲を確認していない。
   - `setServoAngle(NaN)` が範囲チェックを通ってしまう。
   - E-stop の確認と設定の間に競合がある。
   - `lastError()` の値が当てにならない。
   - `end()` の後に `begin()` すると、古い指令が再び送られる。
   - 送信キュー（16）が 1 周期の最大フレーム数（28）より短い。
