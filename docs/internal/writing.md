# 説明の文書の書き方

`docs/guide/` と `docs/spec/` の文書を書くときの決まり（2026-11-15、ユーザの求めで Claude が書いた）。台帳（`decisions/`）とメモ（`notes/`）には当てはめない（そちらは 1 行 1 決定、常体）。

狙いは 1 つ。**その文書を初めて開いた部員が、途中で誰かに聞かずに、読み終えて手を動かせること。**

## 1. 書く前に、枠を埋める

どのページも、先に次の 5 つを決める。`docs/guide/` の各ページの頭にある表がこれ。決まらないなら、まだ書けない。

| | |
|---|---|
| 読む人 | 誰か。1 種類に絞る |
| 前提 | その人が、すでにできること、知っていること |
| 読むとできること | 読み終えた人ができるようになること。「理解する」ではなく、手を動かす形で書く |
| 見せないもの | その人が知らなくてよいと決めたこと。書きたくなっても書かない |
| 材料 | 事実を確かめる元（台帳、ヘッダ、例、ファーム） |

書き終えたページに残すのは、上の 3 行（読む人、前提、読むとできること）だけ。「見せないもの」と「材料」は書く人のための行なので、書き終えたら消す。

読む人ごとの前提は [notes/2026-11-15-v2-roots.md](notes/2026-11-15-v2-roots.md) の層 1 にある。主制御を書く初心者には、CAN、ID、フレームを見せない。

## 2. 事実は、材料で確かめてから書く

- 動作、数字、関数の名前は、台帳かコードを開いて確かめる。覚えや推測で書かない。
- 確かめられなかったことは、書かないか、「未確認」と書く。
- 台帳の決まりと、今の実装がしていることは、分けて書く（「決まりは …。今の実装は …」）。
- コードの例は `examples/` にあるものを引き、どの例かを書く。文書の中だけにあるコードは、ビルドで確かめられず、古くなる。
- 決まりを写さない。決まりの詳しい中身は `docs/spec/` の 1 か所にだけ書き、案内からはリンクする。

## 3. 文の決まり

- **です・ます**で書く。
- **結論を先に。** 段落の最初の文で、その段落が言いたいことを言う。理由と例はその後。
- **1 つの文で、1 つのことを言う。** 「〜が、〜ので、〜ため」とつなげて長くなったら、切る。
- **理由を添える。** 「〜してください」だけで終わらせず、なぜかを 1 文で書く。理由が分かれば、書いていない場面でも読む人が判断できる。
- **具体的に書く。** 「適切な値」ではなく「0.3」。「しばらく」ではなく「0.2 秒」。「エラーになる」ではなく、何が表示されるか。
- **言葉は、最初に出たところで説明する。** 同じものは、最後まで同じ言葉で呼ぶ（「主制御」を途中で「ホスト」「マスター」と言い換えない）。言葉の一覧は `docs/spec/overview.md` の用語集。
- **主語を省かない。** 「送ります」ではなく「主制御が送ります」。誰がするのかが、この分野ではいちばん取り違えやすい。
- **記号で文をつながない。** 文の中で「→」「＝」「／」を使わない（表の中と、線の上のフレームの図はよい）。
- **正直に書く。** できないこと、まだ無いもの、危ない使い方は、隠さずその場所に書く。
- **書かない言葉:** 「簡単です」「〜するだけです」（できなかった人が自分を責める）。「基本的に」「一般的に」「など」での言い逃れ。前置き（「ここでは〜について説明します」）と、最後の繰り返しのまとめ。

## 4. 形の決まり

- **見出しは、中身を言う。**「概要」「その他」ではなく、「電流を絞る」「回らないとき」。
- **段落は短く。** 3〜4 文まで。
- **手順は番号を付け、1 つの番号で 1 つの動作。** 各手順の後に、うまくいったとき何が見えるかを書く（「LED が緑に点きます」）。
- **表は、同じ軸で比べるものにだけ使う。** 文章を表に押し込まない。
- **箇条書きは、並んでいるものにだけ使う。** 理由と結論のように、つながっているものは文章で書く。項目が文になるなら、頭に太字の見出しを付ける。
- **コード、関数の名前、ファイルの名前、ID は `` ` `` で囲む。**
- **リンクは、何が書いてあるかを言ってから貼る。**「詳しい決まりは [bus.md](../spec/bus.md) にあります」。
- 1 ページが長くなりすぎたら、「読むとできること」が 2 つになっていないかを疑う。

## 5. 見本

同じ内容を、悪い形と良い形で。

悪い例:

> ### 概要
> MD は FB 途絶で offline になります。基本的に `update()` を回していれば問題ありませんが、CAN の配線や終端などを確認してください（→ 0x320〜 の FB が来ているか）。

良い例:

> ### `online()` が false のまま
> ライブラリは、その基板からの知らせを 0.2 秒受け取れないと、`online()` を false にします。つまり、基板の声が主制御に届いていません。次の順に確かめてください。
>
> 1. **基板の電源。** 基板の LED が点いているかを見ます。消えていれば、電源が来ていません。
> 2. **CAN の線。** H と L が入れ替わっていないかを見ます。入れ替わっていると、どの基板とも話せません。
> 3. **基板の番号。** プログラムの `can.md(0)` の 0 と、基板のスイッチの番号が合っているかを見ます。番号の決め方は [今ある基板](../boards.md) にあります。

良い例がしていること: 見出しが症状そのもの。最初の文で何が起きているかを言う。主語がある。数字がある。確かめる順が番号で、1 つずつ。見せないもの（ID）を出していない。

（この見本の中身は書き方を示すためのもので、事実の確認はしていない。実際のページでは 2 節のとおり確かめる。）

## 6. 書き終えたら

- 枠の「読むとできること」が、このページだけでできるか。前提に書いていない知識を使っていないか。
- 「見せないもの」が出ていないか。
- 数字、関数の名前、動作を、材料と突き合わせたか。
- 引いた例がビルドできるか（`examples/` の中で `pio run`）。
- リンクの先があるか（`docs/spec/` は `python3 tools/spec_check.py` が確かめる）。
- 声に出して読んで、息が続かない文が無いか。
