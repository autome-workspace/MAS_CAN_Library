### 実装（2026-10-15、Claude）で台帳に無いまま仮決めした 6 件

確かめて `api.md` に書くか、直す。

- サーボの較正の既定（`configCalibration` を呼ばないとき）は ±π/2 rad ↔ 500〜2500 µs。
- 範囲外の ch（MD の 32 以上など）を求めると、何もしない取っ手（`ch()` が 255）を返し、`error()` には残さない。
- `flush()` の「時計を数え直す」は束ごと（送った束だけ、その束の周期を数え直す）。全部を数え直すと、毎回 `flush()` したときに変わらない束が送られなくなるため。
- 汎用ピン、エアー、ソレノイドの取っ手は、値を覚えるだけで送受信しない（線の上の形が未決）。
- バスの使用率のスタッフィングは、詰める部分の 1 割と見積もる。
- FB を切った MD（設定 35 ＝ 0）は、刻みを書けないので ready にならず、止める値を送り続ける。

### API の保留

- **設定の読み書き API の詳細設計（API-68）**: 低レベルの生 read / write（揮発）のシグネチャと、先に足す型付き関数の範囲（項目 0〜4、MD 32〜46 等）。フラッシュ保存・初期化（A5）は当面道具の担当で保留。
- **`can.error()`（API-47）**: いくつの異常を、いつまで持つか（最後の 1 つだけか、履歴を持つか、読んだら消えるか）。
- **SYNC の送り手が 2 台になる穴（A10）**: `setSyncSource(false)`。遭遇が稀なので保留の穴とする（`0x002` を受けたら他の送り手がいると分かる）。
- **loop 内の確保失敗の細部**: `error()` の `OutOfMemory` で知らせる方向（API-38）。
- **汎用ピン・エアー・ソレノイドの未決**: ソレノイドの `pulse(ms)` をどちらが計るか、`read()` の閾値、汎用出力と汎用入力の設定の種類をまとめるか。

- **将来目標（2026-11-15、ユーザ）**:
  - 指令の送り遅れを主制御の側で見張り、`can.error()` で知らせる（`loop()` が止まって基板が 100 ms の途絶で止まる前に気づくため。サーボにも効く）。
  - E-stop が掛かった、解けたときのコールバック（今は `can.estopped()` と `w.estopLatched()` を読みに行くだけ）。
  - API-24 の「解除を送り直してもラッチが残れば異常と同じ道で知らせる」を実装する（今は知らせずに見張りをやめる。`spec-audit` の A14）。
- **検討メモ（2026-10-15〜16、ユーザ）**:
  - PC でデバッグするときの扱い。主制御がいるなら PC は監視だけ、になりそう。今は決めない（C-78）。
  - 主制御に設定を要求できるようにする案（主制御がバスの上で名前を持つことになる）。
  - 正式版の後、更新の開発は `dev/v1.0.1` のようなブランチに伸ばすかもしれない（versioning.md）。
  - 全基板の帯域の使用率の目安は、ユーザがまとめる予定。DJI のモーターを同じバスに載せると 1 台 1 kHz の FB で重い（C-24）。

  - 足す候補の種類（今は使う予定なし）: 電源の監視、ステッピングモーター（M-49 と一緒に考える）、IMU、CAN 越し I2C/SPI ブリッジ、CAN 越しファーム書き込み（class 7）。色センサ、表示・ブザーは今は要らない。

  - 部の mas libraries（organization の private）に移すときの置き方（`lib/mas/` がそのまま直下になるリポジトリ構成など。トークンを URL に書かない）。
