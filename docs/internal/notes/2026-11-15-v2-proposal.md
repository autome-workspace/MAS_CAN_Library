## 0. 先に結論

- v1 の歪みの根は 1 つにまとまる。**種類ごとに、ID の範囲、フレームの形、束、止め方、設定、主制御の処理を誂えている**こと。MD とサーボの 2 種類で有効な決定が 202 行あり、需要にある残りの種類（エアー、汎用 I/O、ToF、エンコーダ、IMU、コントローラ、NeoPixel、電源、ステッピング、ブリッジ、ファームの書き込み）を同じやり方で足すと、決定もコードもそのぶん増え続ける。今「手に負えない」のは、この先の大きさが見えているからでもある。
- 勧めるのは**案 1「ユニットとプロファイル」**。線の上の単位を「基板の上の機能のかたまり（ユニット）」にし、どのユニットも同じ 4 つのフレーム（状態、指令、データ、設定）を同じ決まりで使う。種類の違いは「プロファイル」という 1 枚の表に閉じ込める。主制御と基板のコア（核）は種類を知らず、**種類をいくつ足しても核の大きさが変わらない**。
- これは CANopen（産業用の CAN の規格）と同じ骨格の、小さな写しになる。実績のある形で、独自の発明ではない。
- 白紙から作るので手間は大きい（4〜6 週間）。先に 1 週間の試作（核 ＋ MD 1 種類 ＋ PC のテスト）で、核が決めた上限の行数に収まるかを確かめてから決めるのがよい。
- 比べる相手として、案 2（ch の考えを残して直す）と案 3（v1 から引くだけ）も書いた。

これを同じ仕組みで受けるには、次の 4 つの型が要る（requirements §4.6 の 3 つの型に、基板の状態を足したもの）。

1. 主制御 → 基板の「今の指令」（周期。途絶えたら安全側）
2. 基板 → 主制御の「今のデータ」（周期、または変化したらすぐ）
3. 聞いて答える（設定、命令）
4. 基板が自分のことを知らせる（いる、止まっている、異常、再起動した）

## 3. 案 1: ユニットとプロファイル（勧め）

### 3.1 骨組み

**ユニット** ＝ 基板の上の機能のかたまり（MD 1 ch、MD 4 ch、サーボ 8 ch、ToF 1 個、など）。番号は 0〜63。基板は 1 つ以上のユニットを持ち、番号は基板のスイッチなどで決める（CAN-Servo 基板なら、サーボ 8 ch のユニットと MD 4 ch のユニットで連続した 2 つ）。

**ID は全種類で 1 つの式。**

```
ID ＝ class × 256 ＋ ユニットの番号 × 4 ＋ 枠（0〜3）
```

| class | ID | 中身 | 向き |
|---|---|---|---|
| 0 | `0x000`〜 | 全体（E-stop、解除、時刻合わせ） | 主制御 → 全部 |
| 1 | `0x100`〜 | ユニットの**状態**（枠 0）と**自己紹介**（枠 1） | ユニット → |
| 2 | `0x200`〜 | **指令**（枠 0〜3） | → ユニット |
| 3 | `0x300`〜 | **データ**（枠 0〜3） | ユニット → |
| 4 | `0x400`〜 | **設定**（枠 0 要求、枠 1 応答） | 往復 |
| 5 | `0x500`〜 | 分割して流すもの（文字、ブリッジ） | 後で |
| 6 | `0x600`〜 | 自作 | |
| 7 | `0x700`〜 | ファームの書き込み | 後で |

例: ユニット 12 の MD は、状態 `0x130`、指令 `0x230`、FB `0x330`、設定 `0x430`／`0x431`。**下 2 桁が同じなら同じユニット**なので、線を生で見ても追える。

**プロファイル** ＝ ユニットの種類を書いた 1 枚の表。中身は次だけ。

- 指令の枠 0〜3 のそれぞれの形（何 byte、どの欄が何か）、途絶えたときの安全側の動作
- データの枠 0〜3 のそれぞれの形、送る周期の既定
- 設定の項目の表（番号、型、範囲、保存できるか）
- 異常の bit の意味

この表は C のヘッダ 1 つに書き、主制御、基板、PC の道具で共有する。仕様書の辞書の部分と DBC は、この表から機械で作れる（C-3 の DBC は v1 でまだ無い。11-14 の B17）。

### 3.2 どのユニットにも共通の決まり（これで全部）

| 決まり | 中身 |
|---|---|
| **状態のフレーム**（class 1、枠 0。例: 5 Hz ＋ 変わったらすぐ） | 動いているか止めているか、**止めている理由の番号**（起動直後、途絶、E-stop、こなせない指令、保護）、E-stop のラッチ、**起動の印**（起動のたびに変わる値）、異常の bit（32 bit） |
| **自己紹介**（class 1、枠 1。起動したときと、例: 1 Hz） | プロファイルの番号と版、基板の種類、ファームの版、固有 ID の一部 |
| 指令の途絶 | 指令の枠ごとに 100 ms。途絶えたらプロファイルの安全側の動作。ラッチしない |
| E-stop | `0x000` で全ユニットが安全側にしてラッチ、署名つきの解除。v1 と同じ |
| 起動 | 最初の有効な指令まで動かない。許可制は無い。v1 と同じ |
| **指令の意味は設定で変えない** | 指令のフレームは、それだけで解釈できる（単位を設定で変える仕組みを持たない）。D1 の再発を、決まりとして禁じる |
| 設定 | ユニット宛ての「聞いて答える」。項目の番号と、ユニットの中の何番目か（副番号）で指す。読む、書く、保存、初期化。値は 3 層（焼いた値 → 保存した値 → 上書き。C-5 のまま） |
| 宣言した設定の書き直し | 主制御のプログラムが `config…` で宣言した値は、ライブラリが覚え、そのユニットが現れるたび（起動の印が変わるたび）に書く。全種類で 1 つの仕組み |
| 番号の重複 | 自分の状態のフレームの ID を他人から受けたら、黙って LED で知らせる（CAN の部品は自分の送ったものを受けないので、受けたら重複） |
| 時刻 | 時刻合わせのフレームと 2 byte の時刻の欄（v1 の C-32、C-38 の形）を、時刻の要るプロファイルだけが使う部品にする。安全とは切り離す |

これで D2（名前が無い）、D3、D5、D7 が消える。起動の知らせ、再起動の推理、異常の読み直し、FB の無い種類の生存、版の確認は、状態と自己紹介の 2 本に吸収される。起動の猶予（C-89）は、刻みが無くなるので要らない。

### 3.3 需要の載せ方（プロファイルの下書き）

中身は例で、決めるのは種類ごとに作るとき。ここで見たいのは「同じ仕組みに全部載るか」。

| 需要 | プロファイル | 指令の枠 | データの枠 |
|---|---|---|---|
| MD 1 ch | MD | 枠 0: 指令の種類 1 byte ＋ 値 float32（duty、A、rad/s、位置）＋ 余りにフィードフォワードなど | 枠 0: 状態、電流、速度、位置 |
| MD 4 ch（CAN-Servo の MD 部） | MD × 4 | 枠 0〜3 が ch 0〜3。形は MD と同じ | 枠 0〜3 が ch 0〜3 |
| 足回りの中継役（C610、XDrive） | 足回り 4 輪 | 枠 0: 4 輪の速度をまとめて（種類は必ず同じなので束にしてよい） | 枠 0〜3 |
| ステッピング | MD（位置、速度だけこなせる） | 同じ | 同じ |
| サーボ 8 ch | サーボ 8 | 枠 0: 8 × 1 byte（v1 の S-2 のまま） | 無し（生存とラッチは状態のフレーム） |
| エアー、ソレノイド | 弁 | 枠 0: 1 ch 1 bit。枠 1: 時間つきの 1 発（形は要検討） | 無し |
| 汎用 I/O 4 本 | I/O 4 | 枠 0: 4 × uint8 | 枠 0: 4 × uint8 ＋ 変化した時刻 |
| エンコーダ | エンコーダ | 無し | 枠ごとに 1 個: 位置 ＋ 時刻 |
| ToF（マトリクス） | ToF マトリクス | 無し | 枠 0: 見出し、枠 1: 区画（tof-draft の形のまま） |
| ToF（単点） | ToF 単点 | 無し | 枠 0 |
| IMU | IMU | 無し | 枠 0〜3: RPY、角速度、加速度、四元数（imu-draft の「フレームを選ぶ」がそのまま枠になる） |
| コントローラ | コントローラ | 無し | 枠 0: v1 の形。文字は class 5 |
| NeoPixel | NeoPixel | 枠ごとに 1 列: 描き方の命令（周期ではなく送りきり） | 無し |
| 電源の監視 | 電源 | 無し | 枠 0: 電圧、電流、主電源、非常停止ボタン |
| ブリッジ、表示、ファームの書き込み | — | class 5、7 をユニット宛てに使う | |

束にするかどうかは、**全体の法律ではなくプロファイルごとの選択**になる。種類の混ざらないもの（サーボ、弁、4 輪の足回り）は束で軽く、情報の多いもの（MD）は 1 ch 1 本で豊かに送る。D4 の衝突は起きる場所が無い。位置の指令も float32 がそのまま入る（M-49 の宿題が解ける）。

### 3.4 コードの形

- **主制御の核**: ユニット 64 個分の表。ユニットごとに、送る 8 byte × 4（周期、変わった印）、受けた 8 byte × 4（受けた時刻）、状態、宣言した設定の一覧。やることは「受けて表に置く、周期の来た枠を送る、状態を見る、宣言した設定を書く、E-stop」。種類を知らない。ID からユニットは割り算 1 回で決まる（探さない）。
- **取っ手**（`Md`、`Servo` など）: 表の 8 byte を読み書きする薄い関数の集まり。種類 1 つにつき 1 ファイル。
- **基板の核**: 全体のフレーム、状態と自己紹介、指令の枠の途絶、設定の表を引く汎用の読み書きと保存。種類を知らない。
- **基板のプロファイルの部品**: 「指令の 8 byte（無ければ安全側）を受け取り、データの 8 byte を返す」だけ。
- 上限の案: 主制御の核 350 行、基板の核 350 行、プロファイル 1 つは両側あわせて 200 行。**種類を足しても核は増えない。**

主制御のプログラムから見ると、こうなる。

```cpp
mcan::Host can;
mcan::Md lift = can.md(12);          // ユニット 12 の MD
mcan::Servo hand = can.servo(20, 3); // ユニット 20 のサーボの 3 番

void loop() {
    can.update();
    lift.setSpeed(3.0f);             // rad/s。刻みの設定は無い
    hand.setAngle(0.5f);
}
```

`can.md(12)` と書いたのにユニット 12 がサーボだと自己紹介したら、「ユニット 12 は MD ではない」と知らせられる。`can.print(Serial)` で線の上のユニットの一覧を出せる（UdonLibrary の `show()` にあたる）。

### 3.5 得るもの、払うもの

**得るもの**

- 種類を足す作業が「表を 1 枚書き、取っ手と部品を 1 組書く」になる。核と、共通の決まりは増えない。台帳も「共通」1 冊と、プロファイルごとの短い表になる。
- D0〜D8 が全部消える（D6 のブレーキは MD のプロファイルの中で決め直す）。
- 基板の一覧、種類の取り違え、番号の重複、止まっている理由、FB の無い種類の生存が見える。部員がつまずく所に答えが出る。
- PC の監視が、自己紹介と表から自動で読める。

**払うもの**

- **ch の通し番号が無くなる。**「MD の 3 番」は「ユニット 3」、4 ch の基板は「ユニット 5 の 2 番」になる。基板の印字（番号と端子）とは合うが、v1 の考え方と部員のプログラムの番号は変わる。
- **線の使用率が増える。** 1 本の長さは 47 ＋ 8 × DLC ＋ スタッフィング 1 割で見積もった。

  | MD 16 台、指令と FB を 100 Hz | 指令 | FB | 状態 | 合計 |
  |---|---|---|---|---|
  | v1（4 ch の束） | 4.8% | 19.2% | — | 24% |
  | 案 1（1 ch 1 本、DLC 5） | 15.0% | 19.2% | 1% | 35% |

  MD 24 台なら 36% → 53%。全部を 100 Hz で回す必要は無いので、機構の軸を 50 Hz にする、足回りを 4 輪の束にする、で 40% 前後に戻せる。線を使っているのは今も FB のほう。
- ユニットは 63 個まで、枠は向きごとに 4 つまで（足りない基板はユニットを 2 つ使う）。DJI の固定 ID（C-24）を同じ線に残すなら、ユニット 0〜2 と 63 を空ける。
- FB の電流と速度は、float 2 つが 8 byte に入らない。刻みを「ユニットが自己紹介で告げる、変わらない値」にするか、16 bit の float にするか（問い 6）。
- **ほぼ全部を書き直す。** core、`node`、`Host`、テスト、仕様書。残るのは、ファームのハードウェアの部分（電流ループ、PIO のサーボ、フラッシュ）、取っ手の API の大半、テストの枠組み、台帳の決定のうち動作に関するもの（途絶、E-stop、MD の動作、設定の 3 層）。

**移る手間: 大（4〜6 週間）。** 一度に作らず、縦に薄く作る。

1. 核 ＋ MD のプロファイル ＋ PC のテスト。ここで核が上限に収まるかを見る（1 週間。**ここまでが試作で、だめなら引き返せる**）
2. micro-MD か CAN_MD を 1 枚載せ、2 枚以上を同じ線で試す
3. サーボ 8、CAN-Servo
4. 新しい種類を 1 つ（エアーが需要に近い）。ここで「核に触らずに足せた」ことを確かめてから、形を凍らせる

### 3.6 CANopen そのものを使わない理由

骨格は同じ（ユニットの番号、状態 ＝ ハートビート、指令とデータ ＝ PDO、設定 ＝ SDO）。そのものを採らないのは、仕様が大きく（オブジェクト辞書、PDO の割り付け、通信の状態機械）、状態機械が許可制にあたり（C-4 に反する）、FLASH 32 KB の基板に既製のスタックが重く、部員が全部を読めないため。形だけ借りて、割り付けを固定の表にしたものが案 1。

## 4. 比べる相手

### 案 2: ch の考えを残して直す

宛先は v1 と同じ（種類、ch）のまま、足りないものを足す。

- 刻みを保存できる「機体の値」にして、主制御は読むだけにする（D1）
- 基板ごとの状態のフレームを 1 本足す（D2）。起動の知らせ、異常の読み直し、生存がこれに入る
- 走っている間の `Host` から、MD 専用の設定の処理を抜く（D3）
- MD の指令を 1 ch 1 フレームにする（D4）。サーボは束のまま

得るもの: ch の通し番号と、部員のプログラムの番号がそのまま。D1〜D4 は消える。払うもの: **D0 が残る。** 種類ごとに ID の範囲と形を誂える作りは変わらないので、エアーや ToF を足すたびに、決定と `Host`、`node` の書き換えが要る。基板の状態は「主な種類と k」から ID を作ることになり、種類を 2 つ持つ基板の扱いが揺れたまま。手間は中（3〜4 週間）。

### 案 3: v1 から引くだけ

ID も束も v1 のまま、状態を減らす。刻みを機体の値にする、起動の知らせの ID に先頭の ch を持たせる、SYNC を必須から外す、ブレーキを 1 か所にする、形の無い取っ手と予約を仕様から落とす、主制御は 1 台と決める。

得るもの: いちばん危ない D1 が、数日〜1 週間で消える。`host.cpp` から約 200 行が消える。作業は消すことが中心。払うもの: D0、D2 の残り、D3 の半分、D4 がそのまま。**種類を足す段になると、同じ壁にもう一度当たる。**

### 比べる

| | 案 1 ユニットとプロファイル | 案 2 ch を残して直す | 案 3 引くだけ |

## 5. どの案でも一緒にやりたいこと

- **大きさの上限を先に決め、超えるものは入れない。** ユニットテストと同じく、上限を点検に入れられる。
- **ユーザが読む入口を 1 つ決める。** 基板の核がいちばん向いている（ハードウェアに触らない、テストがある、決まりの大半が動く形で書いてある）。
- I3: MD の電流ループと駆動を、CAN_MD と micro-MD で共有する部品にする。
- I4: 時刻を一周しない形にする。I5: ウォッチドッグを入れる。
- 進め方の連鎖（1.4）を、v2 が固まるまでは軽くする（台帳だけを正本にし、仕様書と artifact は節目で作る）。
- 形を凍らせるのは、2 枚以上を同じ線につなぐ試験と、新しい種類を 1 つ足す試験の後。
- v1 は V9 のとおり `v1.x` の保守ブランチに切り、危ないものだけ直す。

## 追記（2026-11-15）: ユニットは（種類、番号）で指す

上の本文は直さず、ここに足す。ユーザの指摘（2026-11-15）:

- 現行の API は初心者向けも押さえるのが目的で、`mcan::Md arm = can.md(0)`（MD の 0 番をアームとする）の形になっている。
- 基板単位の「ユニット」は理解しづらい。サーボと MD が混在する基板の扱いに困り、v1 は基板単位ではなく ch 単位の区別にした。

これを受けて、案 1 を次のように改める。**ユーザはこの形でよいとした（2026-11-15）。骨格の方向の合意で、台帳の決定はまだ。**

### 改めた形

- **ユニット ＝（種類、番号）で指す、線の上の最小の単位。** 基板のかたまりではない。v1 の「束」を全種類に広げたもの。基板はユニットをいくつか受け持つ入れ物（C-14 の考えのまま）。
- ユニット 1 つの中身は種類ごとに決まる: MD は 1 ch、サーボは 8 ch、エアーは 8 ch など、ToF は 1 個。
- **宛先と API は v1 のまま（種類、ch）。** `can.md(0)`、`can.servo(9)`。番号は種類ごとに 0 から数える。ch からユニットへの対応は割り算で、ライブラリが行う。「ユニット」という言葉は線の上の形を読む人だけが知ればよく、主制御を書く部員には出さない。
- ID の式は `ID ＝ class × 256 ＋ 種類の基点 ＋ 番号`。種類ごとに番号の範囲を表で割り当てる（例: MD `0x10`〜`0x2F`、サーボ `0x30`〜`0x37`。先頭の 16 個は全体のフレームと DJI のために空ける）。MD の 0 番なら状態 `0x110`、指令 `0x210`、FB `0x310`。下 2 桁が同じなら同じユニット、は保てる。枠を複数使う種類（ToF マトリクス、IMU）は、表で 1 ユニットあたりの ID の数を決める。設定の要求と応答の ID の取り方は作るときに決める。
- 3.2 の共通の決まり（状態、自己紹介、途絶、E-stop、指令の意味は設定で変えない、宣言した設定の書き直し、時刻）と、3.4 のコードの形（核は種類を知らない、プロファイルの表）は、そのまま。

### 種類が混在する基板

v1 と同じ。CAN-Servo 基板は、サーボのユニット 1 つと MD のユニット 4 つを受け持つ。どの番号を受け持つかは k とファームの規則で決まる（C-81 のまま）。基板は受け持つユニットの数だけ状態のフレームを出し、再起動すれば全部のユニットが同時に起動の印を変える。同じ基板かは自己紹介の固有 ID で分かる。基板そのものには番号を振らない。

### 本文から変わる所

| 本文 | 追記の後 |
|---|---|
| 3.1 ユニットの番号 0〜63、`ID ＝ class × 256 ＋ ユニット × 4 ＋ 枠` | 上の式。番号は種類ごと |
| 3.4 の例 `can.servo(20, 3)` | `can.servo(ch)`。v1 と同じ |
| 3.5「ch の通し番号が無くなる」「ユニットは 63 個まで」 | 無くならない。上限は種類ごとの表で決まる |
| 3.5 DJI のためにユニット 0〜2 と 63 を空ける | 各 class の先頭 16 個を空ける |
| 問い 2（ch の通し番号をやめるか） | 取り下げ |
| 問い 7（ユニットの番号の決め方） | k の決め方（C-75、C-81）のまま。番号の空間は種類ごとなので、D38 の理由（位置の奪い合い）は v1 と同じに残る |

### 新しく出る点

- 状態のフレームの本数が基板で不揃いになる（サーボ 8 本の基板は 1 本、MD 4 つの基板は 4 本）。MD 24 台、5 Hz で線の 1.4% ほど。
- 基板全体への操作（再起動、まとめて保存）は「その基板のどれかのユニット宛て」に送る。範囲（そのユニットだけか、基板の全部か）を共通の決まりとして明記する（v1 の B8、B9 を最初に決める）。
- ユニットは 1 枚の基板がまるごと受け持つ（v1 の C-20 を指令の側にも広げる）。サーボ 8 ch のユニットを 2 枚の基板で分けることはできない。
- 部員に見せる境界: 主制御を書く部員は「種類と番号」「置いた値が送られる」「online と止まっている理由」まで。ユニット、class、枠、プロファイルの表は、基板を作る人と線を読む人のもの。
