# 原因の特定につながる「読む」API の足りない所（2026-11-15、Claude）

**決定ではない。** ユーザの指摘（11-15）:「今の MAS CAN には、原因特定につながる read 系 API の案内があまりない」。案内（`docs/guide/host/troubleshooting.md` の「プログラムから、原因を絞る」）には、今ある関数での絞り方を書いた。ここには、関数そのものが無くて読めないものを並べる。現場の痛みの 2 つ目（動かない理由が分からない）に効く、v1 の上での直しの候補。

| 読めないもの | 線の上の決まりにはあるか | 足りないもの |
|---|---|---|
| 基板の種類、基板の版、ファームの版、プロトコルの版 | ある（設定の共通の項目 1〜3。C-60、C-63、C-70、C-71） | 主制御のライブラリに読む関数が無い。版の食い違いも知らせていない（C-73、11-14 の点検の A13） |
| 基板が受け持つ ch の範囲、固有 ID | ある（項目 4、0。C-65、C-61） | 同上。同じ ch の基板が 2 枚あるかを調べる手段になる |
| 基板が覚えている設定の値（向き 32、電流の上限 33、止め方 34 など） | ある（MD の項目 32〜46 は読める） | 読む関数も書く関数も無い（API-59 で保留）。別の機体から来た基板の値に気づけない |
| 止めている理由（途絶、こなせない指令、起動直後、保護の区別） | **無い**（M-58「理由を区別する bit は作らない」） | 線の上の形を変える話。v1 では、ほかの値から絞るしかない |
| サーボの基板がいるか、様子 | 決まりはある（サーボの設定 `0x410`。S-11、C-49） | CAN-Servo-v1 のファームが設定に答えていない（11-14 の点検の A1）。ライブラリも MD の設定しか扱わない |
| 過去に起きたこと | — | `can.error()` は最後の 1 つだけ（API-47 の未決）。基板の再起動を見たこと、設定を断られたこと、の履歴が無い |
| 基板の再起動があったこと | 起動の知らせと異常の bit 0 がある | ライブラリは自分で片付けて、アプリに知らせない。位置の原点を使うアプリは知りたい |

手を付けるなら、上の 3 行（項目 0〜4 と 32〜46 を読む）がいちばん安い。線の上の形は変わらず、主制御のライブラリに「設定を読む」関数を足すだけで、スキャナにも基板の種類と版を出せる。台帳では API-59（機体の値を書く `config` と保存の API）と一緒に決める、となっている。
