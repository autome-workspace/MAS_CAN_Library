層 1 から出ること（Claude。11-15 に見せて「ok」）:

- U3 から: ライブラリは、基板の側にも「マイコンごとの部品」を持つ。中身は CAN の送受信だけでなく、時刻、フラッシュの読み書き、固有 ID、再起動、ウォッチドッグまで（今は 3 つのファームが別々に書いていて、片方だけ直って食い違っている）。基板を作る部員が書くのは、モーターやセンサを動かす部分だけになる。STM32 は系列で CAN の部品が違う（F0 などの bxCAN と、G4 などの FDCAN）ので、「一度用意すれば」は系列ごと。ピンとクロックは基板ごとに残る。
- U4 から: Python で主制御をもう 1 つ書くと、G1 の「1 つのライブラリ」が PC の側で崩れ、握手や状態の処理が二重になる。ROS 2 なら、C++ の `Host`（SocketCAN の口を足す）を包んだノードを 1 つ用意し、Python の人はトピックで使う形が、実装を 1 つに保てる。分からないうちは決めず、`Host` をマイコンに依存させないこと（今もそう）だけ守る。

補足（Claude、仮）:

- 1 の限度: 人が掛けた E-stop と、指令の途絶（100 ms）で止まることは、1 より上。

- 4 と 6 がぶつかったら 4 を取る。

### この順位から決まること（Claude）

| 決まること | 前提 |
|---|---|
| 握手（設定を書いてから許可）は残す。うまくいく道では、再起動から動き出すまでが 0.1 秒ほど延びるだけ | 2 位。1 位をほとんど損なわない |
| **設定の書き込みが通らなくても、許可して動かし、通らなかった項目を記録する**（draft の「だめ」の状態で止めるのをやめる）。プロトコルの版が合わなくても、知らせて動かす | 1 位が 2 位より上。確認 11-15（ユーザ:「まるで PC の OS。ひとつひとつの小さいエラーに止まっていられない」）。代償: 保存した上限 15 A、プログラムは 3 A、書き込みが通らないと 15 A のまま動く |
| ほかの主制御が持つユニットには指令しない | 2 台が出し合うと、動くことにもならない |

| 状態のフレームに、止めている理由の番号を載せる（M-58 の見直し） | 3 位 |
| 線を録った記録だけで、何が起きたかを読める形にする | 3 位 |

| 記録には重さを付ける（知らせ、警告、重い）。止まるのは、人が掛けた E-stop と指令の途絶だけ。重いものはアプリが拾って自分で止められる | 1 位と 3 位は一組（止まらないのは、記録が残るから）。G3（初心者は何もしなくても動き、慣れた人は拾える）。Claude、仮 |

| E8 | DJI の固定 ID（`0x1FE`〜`0x1FF`、`0x200`〜`0x20B`、`0x2FE`〜`0x2FF`）は使わない。DJI の機器が同じ線に載ることがある（層 2） | C-24、11-15 ユーザ | 確認 11-15 |

DJI を載せることの代償（Claude。使う人が知っておくこと）:

- C610 の FB は 1 台 1 kHz で止められない。4 台で線の約 5 割（requirements §4.8 の見積もり）。層 3 の帯域の目安（5 割）を、それだけで使い切る。
- DJI の FB の ID（`0x201`〜）は、MAS CAN のどの指令（`0x210`〜）より優先される。MAS CAN のフレームは待たされる。
- 過去の機体（R2）では、この流量で主制御の受信が溢れた。
- DJI の機器は、状態のフレームも握手も E-stop も知らない。止めるのは主制御（指令を 0 にする）。
- したがって「載せられる（ID はぶつからない）。帯域と受信の溢れは、線の使用率を見て使う人が判断する」とする。MAS CAN のユニットを多く載せる線とは分けるか、中継役を挟むのが無難。DJI 用の取っ手をライブラリに入れるかは、需要が出たときに決める。

## 層 6: 種類ごとの形

決めるのは、層 2 の「今ある」「近い」だけ（MD、サーボ、コントローラ、エアー）。順位 7（v1 のまま。変えるには理由が要る）に照らして、v1 から変える所だけを挙げる（Claude）。

### MD

| v1 から変える所 | 来る元 |
|---|---|
| 指令は 1 ch 1 本（`0x210` ＋ ch、DLC 3）。byte 0 ＝ 指令の種類（v1 の番号: 0 電流、1 速度、2 duty、3 位置）、byte 1–2 ＝ v1 と同じ形の int16。DLC が長いのは許す | S9 |
| 刻み（48、49）は、保存できる普通の項目になる | S4、S7 |
| 起動の知らせ（`0x010`）と起動の猶予（C-89）は無くなり、状態のフレームと握手に替わる | S3、S4 |

**FB は v1 のまま**（M-14〜M-21。`0x320` ＋ ch ではなく番地の式で `0x310` ＋ ch になるだけ）。draft では「8 byte 固定にし、状態の bit を状態のフレームへ移し、空いた欄の duty をやめる」としていたが、取り下げる。

- 来る元が弱い（順位 6 の「そろっている」だけ）。順位 7 に負ける。
- 空いた欄に実際の duty を入れる決まり（M-15）は、電流も速度も測れない基板（CAN-Servo の MD 部）にとって唯一の手がかりで、順位 3（原因をたどれる）に効く。消すのは逆だった。
- FB の状態の bit（止めている、E-stop、異常あり）は 100 Hz の速い写しとして残す。**正本は状態のフレーム**で、理由と持ち主はそちらにだけある。

動作（M-22〜M-31、M-51、M-57〜59）、設定の項目と単位（M-36、M-38、M-41〜M-47、M-54）は v1 のまま。位置の指令は予約のまま（M-49）。

### サーボ

指令の形（S-1〜S-5）、動作（S-7、S-9、S-15）、設定（S-11、S-12、S-14）は v1 のまま。ユニット ＝ 8 ch。変わるのは共通の部分だけ（状態のフレームを出す、握手、設定に答える。v1 の CAN-Servo は設定に答えていない）。

### コントローラ

フレームの形は v1 のまま（controller-draft、API-54）。番地を取り直す。基板が実在するかは不明なので、作るときに確かめる。

### エアー、ソレノイド

形は、最初の基板を作るときに決める（ユニットの大きさも）。今は、骨格が邪魔をしないことだけ確かめた: 指令は 1 本に 1 ch 1 bit で入る。データは無く、生存とラッチは状態のフレームで分かる。途絶で「そのまま」を選ぶのは設定の項目。ソレノイドの時間つきの 1 発は、指令の欄の使い方として作るときに決める。

### まとめ: v1 から本当に変わるもの

- 共通: 状態のフレーム、握手と持ち主、主制御の状態のフレーム、値の 4 段（保存できない項目の区別が無くなる）、設定の宛先と並行、履歴、ID の式。
- MD: 指令が 1 ch 1 本。
- それ以外の種類ごとの形と動作は、v1 のまま。

## 現場で痛かったこと（2026-11-15、ユーザ。雑談の中で出た）

層 0〜4 に入っていなかった事実。**優先順位（層 3）は、この痛みからではなく、11-15 のユーザの選び方から Claude が読み取ったもの**なので、ここと突き合わせて見直す。

- v1 は部でかなり使われている。ちゃんと動いてはいる。
- v2 を検討し始めたのは、ユーザが「汚い」「メンテナンス性に乏しい」と感じたから。「v1 に大きく問題があるかと言われたら、まだそこまで」。
- 実際に当たった課題:
  1. ユーザを通さないと、新しい基板のファームがほとんど書けない。
  2. 動かない理由が分からない（特定する材料は API にあるので、「使い方が分からない」にまとまる）。
  3. 利用者向けの説明が浅かった。スキャナの実装なども入れるべきだった。

Claude の見方: 11-15 にいちばん時間を使った握手、持ち主、起動の印、状態の表は、この 3 つにほとんど効かない。効くもの（マイコンごとの部品、基板側のコアがサーボなども受け持つ、スキャナと一覧、説明）は、v1 の線の上の形のままでも作れ、v2 でも要るので無駄にならない。かなり使われている v1 の互換を切る理由としては、今のところ弱い。

## 別の目での点検（2026-11-15、経緯を知らないセッション）

## 今の位置: v2 は保留（2026-11-15、ユーザ）

**v2 は保留にし、先に v1 の上で、現場で痛かった 3 つを直す**（ユーザ「はい」）。このメモと、同じ日の proposal、scenes、draft は、設計の検討として残す。コードにはしていない。台帳にも書いていない。

先に直すもの（どれも v1 の線の上の形のままでき、v2 に進んでも無駄にならない）:

1. 基板のファームを、ユーザを通さずに書けるようにする（基板の側のマイコンごとの部品、基板側のコアがサーボなども受け持つ）。
2. 動かない理由が分かるようにする（スキャナ ＝ 線につないだら何がいるかの一覧、主制御の側の一覧）。
3. 利用者向けの説明。

層 0〜4（目的、使う人、載せるもの、優先順位、前提）は v1 の直しにもそのまま使う物差し。

v2 に戻るきっかけ（Claude の案。どれかが起きたら）:

- PC とマイコンの 2 台で、v1 の形では実際に困った。
- 3 つ目の種類（エアーなど）を足そうとして、種類ごとに誂える作りが壁になった。
- 時刻合わせを使う基板を作ることになった。

戻るときは、上の「別の目での点検」の重い 6 件（刻みと「通らなくても動かす」の矛盾、v1 の電流の指令との ID の重なり、E-stop が解除できなくなる、送信の待ち行列、持ち主の穴、主制御の再起動でエアーの保持が消える）から始める。
