# 主制御のライブラリの見直し（2026-10-16、Claude）

対象は `lib/mas` の主制御側（コミット `5bd2201` の時点）。小さい問題ではなく、根幹の作りに違和感がないかを見た。決定ではない。決めたことは台帳に書く。

骨組み（取っ手は Host の中身を指すだけ、`update()` がすべてを進める、core の C を基板と共有する）には違和感はない。気になったのは下の 3 つ。1 と 2 は動いている最中のモーターに出る。

## 1. 基板が 1 枚再起動すると、同じ線の MD が全部しばらく止まる

### 今の動き

起動の知らせ（`0x010` ＋ 種類）は DLC 0 で、どの基板からかが分からない。そこでライブラリは、FB を受けたことのある MD 全部の刻みを「未確認」に戻す（`host.cpp` の `receiveAll` → `onMdRestart`）。未確認の ch は `ready()` が false になり、止める値を送る（API-43）。結果として、1 枚の再起動でその線の MD が全部止まる。

### 試した結果

偽のポートで試した（MD 8 個、loop 100 Hz、基板は次の周期までに応答する前提）。

```
after boot t=  0 ms: not ready=8
after boot t= 80 ms: not ready=4
after boot t=160 ms: not ready=0   ← 160 ms 全停止
```

### 問題

- 設定の要求は 1 回の `update()` に 1 つしか進まない（C-51 の「1 つずつ」）。MD 8 個 × 刻み 2 つで 16 周期かかる。loop が 20 Hz（API-10 の下限）なら 800 ms。
- 書き直す順番は連結リストの順で、再起動した基板が最後になることもある。そうなると起動の猶予（C-89、200 ms）を過ぎてから刻みが届き、猶予の狙いが MD の数と loop の速さによっては成り立たない。
- 処理が二重に走る。起動の知らせに加えて、異常の詳細の bit 0（再起動）を読んだときにも `onMdRestart` が呼ばれる。その ch はもう一度止まり、`relink` も 1 回余分に走って位置の差分を 1 回落とす。
- 再起動していない MD も `relink` で FB 1 回分の位置の差分を捨てるので、位置が少しずれる。

### 台帳との関係

「その種類の ch に止める値を送る」は C-87 で、取り消されて C-88（先に送り直すだけ）と C-89（猶予）に置き換わっている。実装は事実上 C-87 に戻っている。

### 直し方の案

- **(a) ライブラリだけで直す（勧める）:** 起動の知らせでは送り直しの印を付けるだけにし、`ready()` は落とさない。再起動した基板は猶予（C-89）で守る。止める値は、異常の詳細の bit 0 でどの基板かが分かった ch にだけ送る。位置の `relink` も、どの基板かが分かった ch にだけ行う。二重の処理もここで片付ける。
- **(b) 線の上を変える:** 起動の知らせに先頭の ch と数（2 byte）を載せ、どの基板かをすぐ分かるようにする。戻せない変更だが、今はまだ alpha（`1.0.0-alpha.1`）。

(a) を先に入れ、(b) は版を上げる前に検討する、を勧める。どちらにするかはユーザが決める。

## 2. FB の換算に、基板にまだ届いていない刻みを使っている

### 今の動き

`fb.speed` と `fb.current` は、ライブラリが持っている刻み（`speed_lsb_rpm`、`current_lsb_ma`）で換算している（`handleMdFeedback`）。これはアプリが望む値で、基板が実際に使っている値とは限らない。ずれる場面は 3 つ。

- 主制御を起動した直後。基板には前のプログラムの刻みが残っている。
- 基板が再起動した後。基板は既定値の 1.0 に戻っている（M-56、保存しない）。
- 走行中に `configSpeedResolution` などを変えたとき。

### 試した結果

起動直後の最初の FB で `speed()=2.09`（本当は 10.47 rad/s）。基板に前の刻み 0.5 rpm/LSB が残り、ライブラリは 0.1 rpm/LSB で換算したため。

### 問題

指令は止める値に抑えているので、危険は小さい。ただ、`speed()` や `current()` をそのまま制御やログに使うアプリにはおかしな値が渡る。

### 直し方の案

元をたどると、ch の状態に「アプリが望む刻み」と「基板で確かめた刻み」の区別がない。2 つを分けて持ち、FB は確かめた刻みで換算し、確かめるまでは速度と電流を無効として扱う（`speedValid()`、`currentValid()` を false にするなど）。1 と同じ所（刻みの状態）を触るので、一緒に直すのがよい。

## 3. Host が MD 専用の作りになっていて、種類を足すたびに Host を書き換えることになる

### 今の作り

- 設定の要求の仕組みに MD が直書きされている。`serviceSettings` の `MAS_CAN_KIND_MD`、MD の応答 ID しか受けない `receiveAll`、MD の用途だけの `ReqTag`。
- 種類ごとの処理が Host の 5〜6 か所に散らばっている（`obtain`、`receiveAll`、`update` の online の判定、`sendMd`／`sendServos`、`waitReady`、`resetCommands`）。
- ch はすべて 1 本の連結リストに入っていて、`sendMd` と `sendServos` は毎回 ch ごとにリストを先頭からたどる（1 回の `update()` で 96 回）。

### 問題

今は MD とサーボだけなので困らない。サーボの `config`（API-59）や汎用ピンを線に載せるときに、ここで詰まる。

### 直し方の案

種類ごとに「ch → 中身」の表を Host に持たせ、設定の要求も種類を持てるようにする。表にすると、毎回リストをたどる処理も無くなる。急ぎではなく、次の種類を足す前で足りる。

## 次の手順
