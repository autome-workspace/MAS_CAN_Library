# 場面ごとの流れ

電源を入れてから動き出すまで、止まるとき、再起動したときなどに、主制御と基板が何をして、線の上にどのフレームが流れるかを、場面ごとに通して見せます。

[overview.md](overview.md) の次に読む文書です。その後は辞書（[bus.md](bus.md)、[md.md](md.md)、[servo.md](servo.md)、[settings.md](settings.md)、[ids.md](ids.md)、[board.md](board.md)）を、必要なところだけ引いてください。

## この文書の読み方

各場面は次の 4 段で書きます。

| 段 | 中身 |
|---|---|
| 何が起きるか | 主制御、基板、ポートが順に何をするか。流れが分かる最小限と、決まりの理由 |
| 線の上 | フレームの並び。実際に主制御と基板を話させて取ったバイト列 |
| 今の実装 | `lib/mas` と既存のファームが、どの関数でそれを行うか。台帳で決めていないことを、今の実装がどうしているか |
| 決まりの場所 | 関わる決まりの辞書と、台帳の番号 |

- 「今の実装」は台帳の決まりではありません。ライブラリやファームを直せば変わります。基板のファームを自分で作るなら、「決まりの場所」の側に従ってください。
- 決まりの細部は、この文書では言い直しません。食い違ったら辞書が正しいです。

### 登場するもの

| 名前 | 何か |
|---|---|
| 主制御 | 指令を出す側。`lib/mas` の `Host`（`include/mas/can/host.h`、`src/can/host.cpp`）。MD の取っ手は `Md`、サーボの取っ手は `Servo`（`include/mas/can/device/`） |
| アプリ | 主制御の上で `Host` を使うプログラム |
| 基板 | 指令を受けて動く側 |
| node | 基板側のコア（`include/mas/can/node.h`、`src/can/node.c`）。MD だけを扱う |
| ポート | 基板のファームのうち、ハードウェアに触る自前の部分（CAN、時計、フラッシュ、モーター） |

### 線の上の表の読み方

- バイト列は、PC の上で主制御（`Host`）と基板（node）を偽のバスでつないで話させ、線に出たフレームを書き出したものです。組み立ては `lib/mas/test/test_roundtrip.cpp` と同じです。
- サーボの基板は node では動かせません。サーボの場面は主制御が送るフレームだけを取り、基板の動きは `firmware/CAN-Servo-v1/src/main.cpp` を読んで書きました。
- 時刻の目安は、場面の始まりからの ms です。1 ms 刻みで進め、主制御の `update()` も 1 ms ごとに呼びました。実機では、ループの速さや送信の待ちで数 ms ずれます。
- 向きの「主 → 基」は主制御から基板、「基 → 主」は基板から主制御です。
- 同じフレームの繰り返しは「以後 10 ms ごと」とまとめ、表から省きます。ID が「—」の行はフレームではなく、主制御か基板の中で起きたことです。
- SYNC の値は、主制御の起動からの µs です。この例の時計は 5 秒から始めてあります。
- FB の測った値は、指令どおりに動く理想のモーターのものです。電流は 0 のまま、位置は数えていません。

### 例の条件（MD）

断りが無ければ、MD の場面は次の条件で取りました。

| | 条件 |
|---|---|
| 基板 | MD の 1 ch の基板。MD の ch 0 を受け持つ。電流と速度を測れる。項目 34 は焼いた値の 0（空転）、項目 35 は焼いた値の 100 Hz |
| アプリ | `Md w = can.md(0)`、`w.configSpeedResolution(0.01f)`（速度の刻み 0.01 rad/s）、`w.setSpeed(5.0f)`（5 rad/s） |
| 線の上の値 | 速度の刻み 0.01 rad/s ＝ 0.0954930 rpm。項目 49 に float32 `3D C3 91 D0` を書く。5 rad/s ÷ 0.01 ＝ 500 ＝ `01 F4` |

## 1. 電源投入から動き出すまで

例の条件: 上の MD の条件です。主制御と基板の電源を同時に入れました。時刻 0 は、基板が起動の知らせを積み（`mas_can_node_ready`）、主制御が `begin` を済ませたときです。

### 何が起きるか

1. 基板のポートが、出力を止めた状態で起動します。k を読み、node が保存した設定を読み、CAN を始めます。
2. 基板が起動の知らせ `0x010` を送ります。ここから FB を送り始め、200 ms の起動の猶予に入ります。猶予の間は指令に従いません。異常の詳細の bit 0「再起動した」が立っています。
3. 主制御は SYNC と指令を送り始めます。刻みをまだ基板で確かめていないので、指令には止める値を入れます。基板に前の刻みが残っていても、桁違いに動かないようにするためです。
4. 主制御は最初の FB を受けると、刻み（項目 49、48）を書きます。刻みは保存できない値で、起動すると 1.0 に戻っているからです。
5. FB の bit 0（異常あり）が立っているので、主制御は異常の詳細（項目 5）を読みます。bit 0「再起動した」が立っていれば、1 を書いて消します。
6. 刻みを確かめたら、主制御は指令に本当の値を入れます。猶予の間なので、基板はまだ従いません。
7. 起動の知らせから 200 ms で猶予が明けます。基板は次の指令から動き出し、FB の bit 4（止めている）が 0 になります。

猶予があるので、主制御は基板が動き出す前に刻みを書き終えられます（C-89、C-88、API-43）。

### 今の実装

基板:

- `mas_can_node_init` が保存した設定を読み（`load`）、異常の詳細の bit 0 を立てます。`mas_can_node_ready` が起動の知らせを送る待ち行列に積み、FB と猶予の時計を始めます。呼ぶ順を守るのはポートです（案内の [node の関数と欄](../guide/board/node.md) の「呼ぶ順」）。
- 猶予の起点は `mas_can_node_ready` を呼んだ時刻です。台帳の起点は起動の知らせを送ったときで、差は線に出るまでの待ちの分だけです（[bus.md](bus.md) の 3.5）。
- 猶予の間に受けた指令は、node.c の `handle_md_command` が捨てます（`mas_can_node_in_grace`）。受けた指令として数えないので、猶予が明けた後は次の指令から動きます。
- 猶予の間の止め方は、台帳では未定です。今の node は項目 34 に従います（`mas_can_md_output` が `brake` に項目 34 を入れる。[md.md](md.md) の 4.6）。
- FB は `mas_can_node_tick` が項目 35 の周期で積みます。

主制御:

- `Host::update` は毎回、受信（`receiveAll`）→ E-stop（`serviceEstop`）→ MD の指令（`sendMd`）→ サーボの指令（`sendServos`）→ SYNC → 設定の要求（`serviceSettings`）の順に進めます。
- 起動の知らせは `receiveAll` が受けますが、まだ FB を受けていない ch には何もしません。刻みは、最初の FB を受けた ch から書きに行きます（`handleMdFeedback` が印を付け、`pickResolution` が選ぶ）。アプリが刻みを決めていない ch にも 1.0 を書きます。速度（49）を先、電流（48）を後に書きます。
- MD の指令の束は、アプリが `setSpeed` などを一度呼んだ ch があるときだけ送ります。刻みを確かめるまで（`w.ready()` が false の間）、その ch には止める値を入れます。
- 異常の詳細は、FB の bit 0 を見て `handleMdFeedback` が読みに行きます。bit 0「再起動した」だけは `handleSettingResponse` が消します。
- 電源を同時に入れると、刻みを 2 回書きます。1 回目は最初の FB を受けたときです。2 回目は、異常の詳細の bit 0 を読み、起動の知らせと結びつかない再起動とみなしたときです（`handleSettingResponse` から `onMdRestart`）。線の上の害はありません。

## 2. 通常の運転

例の条件:

| | 条件 |
|---|---|
| 基板 | MD の 1 ch の基板 2 枚。ch 0 と ch 1。どちらも電流と速度を測れる |
| サーボ | ch 2。受け持つ基板の動きは CAN-Servo-v1 を読んで書く。表は主制御が送るフレームだけ |
| アプリ | 刻みは決めない（既定の 1.0 ＝ 1 rpm/LSB）。起動を済ませてから `m0.setSpeed(5.0f)`、`m1.setSpeed(-2.0f)`、`sv.setPulseUs(1500)` を呼ぶ |

時刻 0 は、アプリが 3 つの set を呼んだときです（起動から 400 ms 後）。

### 何が起きるか

1. 主制御は MD の指令を 10 ms ごと、サーボの指令を 20 ms ごと、SYNC を 50 ms ごとに送ります。
2. 指令は束ごとに 1 本です。MD は 4 ch（ch 0〜3 の速度は `0x218`）、サーボは 8 ch（ch 0〜7 は `0x230`）をまとめます。基板は自分の slot だけを読みます。この例では 2 枚の基板が同じ `0x218` を読みます。指令の束は、複数の基板が別々の ch を読んでかまいません（C-20）。
3. 使っていない slot には止める値を入れます。その slot を読む基板がいても、止まったままでいるようにするためです。後ろの使っていない slot は削って、DLC を縮めます（C-40、C-41）。
4. 基板は ch ごとに、項目 35 の周期で FB を返します。指令とは別の時計で回ります。
5. 指令の形（電流、速度、duty）は ID で表します。形を変えると別の ID で送ります。1 つの束の ch は同じ形で動かします。別の形のフレームを同じ束に送ると、互いの ch に止める値を入れて止め合うからです（C-39）。

### 線の上

| 時刻の目安（ms） | 向き | ID | DLC | data（16 進） | 意味 |
|---|---|---|---|---|---|
| 1 | 主 → 基 | `0x218` | 4 | `00 30 FF ED` | 速度の指令。ch 0 ＝ 48（rpm）、ch 1 ＝ −19。ch 2、3 は使っていないので削った。以後 10 ms ごと |
| 1 | 主 → 基 | `0x230` | 3 | `FF FF 64` | サーボの指令。ch 0、1 は使っていないので 255、ch 2 ＝ 100（1500 µs）。ch 3〜7 は削った。以後 20 ms ごと |
| 1 | 主 → 基 | `0x002` | 4 | `00 52 69 A8` | SYNC。以後 50 ms ごと |
| 10 | 基 → 主 | `0x320` | 8 | `40 00 00 00 30 00 00 00` | ch 0 の FB。bit 6–7 ＝ 1（速度）。電流 0、速度 48。以後 10 ms ごと |
| 10 | 基 → 主 | `0x321` | 8 | `40 00 00 FF ED 00 00 00` | ch 1 の FB。速度 −19。以後 10 ms ごと |

`can.flush()` を使うと、周期を待たずに送ります。アプリが `m0.setSpeed(3.0f)` の直後に `can.flush()` を呼んだとき（時刻 0）:

| 時刻の目安（ms） | 向き | ID | DLC | data（16 進） | 意味 |
|---|---|---|---|---|---|
| 0 | 主 → 基 | `0x218` | 4 | `00 1D FF ED` | すぐ送った。ch 0 ＝ 29（3 rad/s） |
| 10 | 主 → 基 | `0x218` | 4 | `00 1D FF ED` | この束の周期は、flush で送った時刻から数え直す |

指令の形を duty に変えたときです。アプリが `m0.setDuty(0.5f)`（ブレーキ）、`m1.setDuty(-0.25f, false)`（空転）を呼びました:

| 時刻の目安（ms） | 向き | ID | DLC | data（16 進） | 意味 |
|---|---|---|---|---|---|
| 8 | 主 → 基 | `0x220` | 4 | `40 01 E0 00` | duty の指令。ch 0 ＝ `0x4001`（約 +50%、bit 0 ＝ 1 でブレーキ）、ch 1 ＝ `0xE000`（約 −25%、空転）。`0x218` は送らなくなる |
| 18 | 基 → 主 | `0x320` | 8 | `80 00 00 00 00 00 00 00` | bit 6–7 ＝ 2（duty）。電流と速度を測れる基板なので、FB に duty は載らない |

### 今の実装

主制御:

- `Host::sendMd` が束ごとに、その束の ch の値を集めて 1 本にします。止める値で埋めるのと DLC を縮めるのは、core の `mas_can_md_cmd_init`、`mas_can_md_cmd_trim` です。束のどの ch にも set を呼んでいなければ、その束は送りません。
- `Host::sendServos` は、`can.servo(ch)` で取っ手を受け取った時点から、その束を送ります（set を呼ぶまで値は 255）。
- SI の値は、`sendMd` が刻みで割って int16 にします（rad/s → rpm → LSB、A → mA → LSB）。duty は ±16383 にして bit 0 を付けます。丸めは四捨五入です（0.5 → 8192 → `0x4000`。ブレーキなので `0x4001`）。台帳に丸め方の決まりはありません。
- 同じ束の ch に別の形の指令を置くと、束のいちばん小さい ch の形だけを送り、ほかの ch は送りません。その ch の `commandConflict()` が true になり、`can.error()` に `CommandConflict` が残ります。送られない ch は途絶で止まります。
- `Host::flush` は値が変わった束だけを送り、送った束の周期を数え直します。
- `w.online()` は、FB を 200 ms 受けていなければ false になります。

基板:

- node.c の `handle_md_command` が、自分の ch の slot だけを読みます。slot が DLC の外なら受けていない扱いです。指令の形が変わったら、次の `mas_can_md_output` で `reset_ctrl` を立てます。
- FB の duty の bit 0 には、node が常に 0 を入れます（node.c の `send_fb`）。台帳は「指令と同じ形で、実際に出している値」とだけ決めていて、bit 0 まで含むかは未定です（[md.md](md.md) の 3.4）。
- サーボ: CAN-Servo-v1 の `servoReceive` が自分の slot を読みます。201〜254 は 255 と同じに扱います。

## 3. 指令が途絶えたとき

例の条件: MD の条件で、5 rad/s で回っています。主制御のループが 250 ms 止まりました（`update()` を呼ばない）。指令も SYNC も止まります。

### 何が起きるか

1. 主制御の指令が来なくなります。基板は ch ごとに、最後に有効な指令を受けてからの時間を数えています。
2. 100 ms 経つと、基板はその ch の出力を止めます。止め方は項目 34 です。ラッチはしません。FB の bit 4 が立ちます。bit 6–7 は最後の指令の形のままです。
3. SYNC が途絶えたことでは止めません。主制御が生きているかは、ch ごとの指令で見ます。指令が来ているのが、上位が生きている証拠だからです（C-91、C-90）。
4. 主制御が戻って指令を送ると、基板は次の有効な指令から動きます。待つ手続きはありません。

### 線の上

| 時刻の目安（ms） | 向き | ID | DLC | data（16 進） | 意味 |
|---|---|---|---|---|---|
| 11 | 主 → 基 | `0x218` | 2 | `01 F4` | 最後の指令 |
| 12 | — | — | — | — | 主制御のループが止まる |

- サーボ: CAN-Servo-v1 の `servoUpdate` が ch ごとに 100 ms を見て、パルスを止めます。

## 4. E-stop と解除

例の条件: MD の条件で、5 rad/s で回っています。アプリが時刻 5 で `can.estop()`、325 で `can.clearEstop()`、555 で `w.setSpeed(5.0f)` を呼びました。

### 何が起きるか

1. アプリが E-stop を掛けると、主制御はすぐ `0x000` を 1 本送ります。
2. 基板は `0x000` を受けたら、中身を見ずに止めてラッチします。MD はブレーキで止め、FB の bit 4 と bit 5 を立てます。サーボはパルスを止めます。MD をブレーキで止めるのは、電源を切らない場面でも早く止まるようにするためです（M-51）。
3. 主制御は、解除するまで `0x000` を 100 ms ごとに送り続けます。後から起動した基板や、1 本を取りこぼした基板も止めるためです（C-31、C-89）。
4. E-stop の間も主制御は指令を送りますが、中身は止める値にします。
5. アプリが解除すると、主制御は `0x001`（`"clr"`）を送ります。アプリの指令も止める値に戻します。解除の前に指令を安全な値に戻すのは主制御の仕事だからです（M-27、API-22）。ただし今の実装では、duty の ch はブレーキの印が残るので、ブレーキで使っていた ch には `0x0001`（duty 0、ブレーキ）を送ります（止める値は `0x0000`、M-8）。
6. 基板はラッチを解きます。MD は起動直後と同じ状態に戻り、次の有効な指令から動きます。位置のカウンタ、設定の今の値、異常の詳細はそのままです。起動の猶予はありません。
7. 主制御は 100 ms 後に FB の bit 5 を見ます。まだ立っている基板があれば、解除を送り直します（最大 3 回）。
8. アプリが指令を書き直すまで、MD は止める値の指令に従います。

### 今の実装

主制御:

- `Host::estop` が `0x000`（DLC 0）を 1 本送り、`Host::serviceEstop` が 100 ms ごとに送り続けます。`Host::clearEstop` が `0x001` を 1 本送り、`Host::resetCommands` で MD の値を 0、サーボの値を 255 に戻します。指令の形はそのまま残ります。
- E-stop の間の止める値は、`sendMd` と `sendServos` が `estopped()` を見て入れます。
- 他の送り手の E-stop を受けたときも止める値を送りますが、`0x000` は送り直しません。他の送り手の解除を受けたら終わり、アプリの指令を止める値に戻します（`receiveAll`）。
- 解除の送り直しは、`serviceEstop` が online の MD の FB の bit 5 を見て行います。FB の無いサーボは見ません。
- 3 回送り直しても bit 5 が残るとき、何も知らせずに見張りをやめます（`serviceEstop`）。台帳は、そのとき「異常と同じ道で知らせる」としています（API-24）。

基板:

- `mas_can_node_on_frame` が `0x000` で E-stop を立てます（DLC もリモートフレームかも見ない）。起動の猶予の間でも、`mas_can_node_ready` の前でも受けます。`0x001` は DLC 3 と署名を確かめます（core の `mas_can_is_estop_clear`）。ラッチしていないときに `0x001` を受けても何もしません。
- E-stop の間、`mas_can_md_output` は `brake` ＝ true の `STOP` を返します。ブレーキを出せない基板は、ポートが空転に丸めます（CAN-Servo-v1 の `motorUpdate`）。
- 解除から次の指令までの止め方は、台帳では未定です。今の node は項目 34 に従います（`mas_can_md_output`。[md.md](md.md) の 4.6）。FB の bit 6–7 は最後の指令の形のままです（この例では 1）。
- node が止めるのは、次に `mas_can_md_output` を呼んだときです。CAN-Servo-v1 は、受信の割り込みの中で `0x000` を見て、すぐ全部の出力を切ります（`canCallback`）。サーボは `servoUpdate` が、ラッチの間パルスを出しません。解除の後にサーボをどうするかは台帳では未定で、CAN-Servo-v1 は新しい指令が来るまでパルスを出しません（[servo.md](servo.md) の 3）。

## 5. 基板が再起動したとき

例の条件: MD の条件で、5 rad/s で回っています。時刻 5 で基板の電源が一瞬落ち、20 ms 後（25）に起動し直しました。

### 何が起きるか

1. 基板が落ちている間も、主制御は気づかずに指令を送り続けます。
2. 起動し直した基板は、電源投入と同じ流れをたどります（1 節）。刻みは焼いた値の 1.0 に戻り、位置は 0 から数え直します。E-stop のラッチも消えます。
3. 主制御は起動の知らせを受けると、MD の ch に「刻みを送り直す」印を付け、ほかの設定より先に書き直します。どの基板が起動したかは分からないので、指令は止めません。止めると、1 枚の再起動で線の全部が止まってしまうからです（C-94）。
4. 起動の知らせの後に最初に受けた FB で bit 0 が立っている ch を、再起動した基板の ch とみなします。その ch の刻みを 1.0 とみなします。アプリの刻みが 1.0 以外なら、書き直して確かめるまで止める値を送ります。
5. 主制御は異常の詳細を読み、bit 0 を消します。
6. ここまでは起動の猶予の間に済みます。猶予が明けると、基板は正しい刻みで次の指令から動きます。猶予は、このための時間です（C-89、C-88）。
7. 起動の知らせを取りこぼしても、FB の bit 0 から異常の詳細の bit 0 を読んで気づきます。再起動を 2 つの手段で知らせるのは、片方を取りこぼしても気づけるようにするためです（C-69）。
8. 主制御が自分で E-stop を掛けている間なら、100 ms ごとの `0x000` が猶予の間に届き、基板はまたラッチします。

### サーボの基板の場合

CAN-Servo 基板（サーボ 8 ch と MD 4 ch）が起動し直すと、次のことが起きます。

1. 基板は MD の起動の知らせ `0x010` と、サーボの起動の知らせ `0x011` を送ります。MD の分は上と同じに進みます。
2. 主制御は `0x011` を受けても何もしません。サーボにはプログラムの値が無く、送り直すものが無いからです。サーボの指令はそのまま 20 ms ごとに送ります。
3. 基板は猶予の間はパルスを出しません。猶予が明けた後の次の指令から、パルスを出します。
4. サーボには FB が無いので、主制御はサーボの基板が再起動したことを、起動の知らせ以外では知れません。どの基板かは分かりません。

主制御が送るフレームです（サーボ ch 0 を 1500 µs。時刻 45 で `0x011` を受けた）。

### 今の実装

主制御:

- 起動の知らせ（MD）: `Host::receiveAll` が、FB を一度でも受けた MD の ch すべてに、刻みの送り直しの印と「起動の知らせの後」の印を付けます。台帳の「その種類の全 ch」（C-94）より狭いですが、まだ FB を受けていない ch は最初の FB で刻みを書く（API-44）ので、結果は同じです。
- 最初の FB で bit 0: `Host::handleMdFeedback` が `Host::onMdRestart` を呼びます。前の FB で bit 0 が立っていなければ、基板の刻みを 1.0 と確かめた扱いにします。アプリの刻みが 1.0 のままなら `ready()` は true のままで、1.0 以外なら書き直して確かめるまで false です。立っていれば刻みは分からない扱いで、書き直すまで false です。false の間は止める値を送ります。
- 書き直しは、`Host::pickResolution` が `ready()` でない ch を先に選びます。刻みは設定の列より先に書きます。
- 刻みを 2 回書きます（起動の知らせの印で 1 回、FB の bit 0 で 1 回）。この例では 1 回目で書けていたので、止める値を送ったのは 35〜37 ms の間だけで、指令の周期に当たりませんでした。線の上の害はありません。
- 異常の詳細の bit 0 を読んだとき、同じ再起動をもう処理していれば二重に処理しません。取りこぼしていれば `onMdRestart` を呼びます（`handleSettingResponse`）。FB の bit 0 が立っている間は読み直します。間隔は、最後に読んでから 100 ms 経った後の最初の FB で、FB が 10 ms ごとならおよそ 110 ms おきです（台帳 API-66 の言い方は「100 ms ごと」）。
- 位置: `onMdRestart` が、次の FB で位置を結び直す印を立てます。`w.position()` は飛ばずに続きます。
- サーボの起動の知らせは、`receiveAll` が解読しますが、何もしません。

基板:

- MD の分は 1 節と同じです。
- CAN-Servo-v1 は `setup` の最後で `mas_can_node_ready` を呼び、MD の起動の知らせを送り終えてから、サーボの起動の知らせを送ります（`loop` の `servoBootPending`）。サーボの猶予は、`servoReceive` が `mas_can_node_in_grace` で見ます。

## 6. 主制御が再起動したとき

例の条件: MD の条件（前のプログラムは速度の刻み 0.01 rad/s）で、5 rad/s で回っています。時刻 5 で主制御が落ち、300 ms 後（305）に新しいプログラムで起動し直しました。新しいプログラムは `can.md(0)`、`setSpeed(1.0f)` を呼び、刻みは決めません。

### 何が起きるか

1. 基板から見ると、指令の途絶です。100 ms で止まります（3 節）。基板は再起動していないので、前のプログラムが書いた刻み（0.0955 rpm/LSB）が残っています。異常の詳細の bit 0 も立ちません。
2. 新しい主制御は、SYNC と指令を送り始めます。刻みを確かめるまで止める値を送ります。
3. 最初の FB を受けたら、取っ手のある MD の ch すべてに刻みを書きます。アプリが刻みを決めていなければ、既定値 1.0 を書きます。前のプログラムの刻みが基板に残っているので、それを消すためです（API-44）。
4. 書けたと確かめたら、本当の値を送ります。基板は再起動していないので猶予は無く、すぐ従います。
5. 新しい主制御は、前の主制御が何をしていたかを知りません。前の主制御が E-stop を掛けたまま落ちたなら、基板はラッチしたままです。

刻みを書かずに送ると、新しいプログラムの 1 rad/s（1 rpm/LSB のつもりで 10）を、基板は 0.0955 rpm/LSB で読み、0.95 rpm で回してしまいます。

### 線の上

| 時刻の目安（ms） | 向き | ID | DLC | data（16 進） | 意味 |
|---|---|---|---|---|---|
| 1 | 主 → 基 | `0x218` | 2 | `01 F4` | 前の主制御の最後の指令 |
| 5 | — | — | — | — | 主制御が落ちる |
| 10 | 基 → 主 | `0x320` | 8 | `40 00 00 01 F4 00 00 00` | まだ動いている。100 まで同じ |
| 101 | — | — | — | — | 途絶。基板は止まる |

## 7. 設定を読む、書く、保存する、再起動させる

例の条件: MD の 1 ch の基板（ch 0）です。電流のハードウェアの限界は 10000 mA、項目 33 の焼いた値は 5000 mA です。要求は主制御のライブラリを使わず、手で組んで送りました（今のライブラリにはこの節の操作の API がありません。「今の実装」を見てください）。要求は 1 本ずつ、応答を受けてから次を送りました。

### 何が起きるか

1. 主制御が要求を 1 本送ります。宛先は種類（ID。MD は `0x400`）と ch（byte 0）です。
2. その ch を受け持つ基板だけが応答します。受け持つ基板がいなければ、何も返りません。答えるのが 1 枚だけなので、応答どうしが衝突しません（C-49）。
3. 主制御は応答を受けてから次の要求を送ります。応答は通し番号（byte 7）で要求と対応づけます。通し番号は主制御が選び、基板は写して返すだけです（C-48、C-51）。
4. 書くと、基板はすぐ反映し、反映した後の値を返します。能力を超える値は抑えて受け付けます。意味の上でありえない値は断り、今の値を返します（M-43、C-85）。
5. 保存は、保存できる項目（機体の値）だけをフラッシュに書きます。書き終えてから応答します。プログラムの値（刻み）は保存されません。
6. 再起動（項目 6）では、基板は応答を送り終えてから再起動します。主制御が成功の応答を受け取れるようにするためです。再起動した基板は 5 節の流れをたどります。保存した値で起動し、プログラムの値は焼いた値に戻ります。
7. 初期化は、保存した値を消し、保存できる項目を焼いた値に戻します。

主制御のライブラリ（`Host`）が今送る設定の要求は、次の 3 つだけです。

|---|---|---|

| 項目 5 を読む | FB の bit 0 が立っている間、100 ms ごと | `Host::handleMdFeedback` |

- 共通項目 0〜4 や機体の値（MD の項目 32〜46、サーボの項目 32〜34）を読み書きする API は、フラッシュ保存 API（A5）と切り離して低レベルの生 API（揮発）から先に足す方針ですが、まだ実装していません（API-68）。フラッシュへの保存・初期化は当面は道具の担当で保留です。それまでは USB-CAN などで生のフレームを送ります。サーボは既定の値で使います。サーボ宛て（`0x410`）の要求も送りません。
- `Host::serviceSettings` が要求を 1 つずつ送ります。刻みの書き込みを先に、ほかは列（16 本）の順にです。応答は、ch、項目、操作、通し番号がそろったものだけを受けます（`handleSettingResponse`）。
- 応答が 50 ms 来なければ、通し番号を新しくして送り直します。2 回送り直しても来なければ、刻みの書き込みなら `can.onSettingError` を 255 で呼びます。項目 5 の読み消しなら知らせず、次の FB でまた読みに行きます。待つ時間と送り直す回数は、台帳には決まりがありません。
- 刻みの書き込みを断られた（結果 1〜63）か、応答が来なかったときは、1 秒おいて書き直します。抑えて返されたら、その値で換算し、`onSettingError` を結果 0 で呼びます。
- 基板: node.c の `handle_setting` が答えます。受け持たない ch、DLC 8 でないもの、下位 3 bit が 0 でない ID、リモートフレームには答えません。予約の項目（42〜44、47）と知らない項目には、結果 1、値 0 を返します。署名違いの再起動は結果 3、値 0 です（[settings.md](settings.md) の 5 で、値の欄が台帳では未定のところ）。再起動の要求の byte 6 は見ません。
- 異常の詳細（項目 5）は基板に 1 つで、ch ごとではありません（台帳では未定。[settings.md](settings.md) の 7）。
- 保存は、範囲が 0 でも 1 でも、全 ch の分を丸ごと `save` に渡します（中身を更新するのは範囲の ch だけ）。CRC を付けます。保存した値が壊れていたら、起動で異常の詳細の bit 1 を立てます。
- 再起動: node は応答を待ち行列に積み、待ち行列が空になった `mas_can_node_drop_tx` の中でポートの `restart` を呼びます。応答を線に出し終えるのを待つのはポートです。micro-MD、CAN-Servo-v1、雛形（`examples/node_md_rp2040`）の `restart` は最大 10 ms 待ちます。CAN_MD は待たずに再起動します（[board.md](board.md) の「既存のファームが決まりと違う所」）。
- サーボの設定: CAN-Servo-v1 は `0x410` に答えません（項目 32〜34 も、共通の項目 0〜6 も持たない）。

## 8. 線の上の基板を調べる

例の条件:

| 基板 | 受け持つもの | 測れるもの | 基板の種類（項目 1） | 固有 ID（例の値） |
|---|---|---|---|---|
| A | MD の ch 0〜3 | 何も無い | `0x0002`（CAN-Servo 基板）、版 1 | `0xE660A4B1C2D3E4F5` |
| B | MD の ch 5 | 電流だけ | `0x0003`（micro-MD 基板）、版 1 | `0x0000123456789ABC` |

どちらも起動した直後で、主制御は何も指令を送っていません。要求は手で組んで送りました。応答を待つ時間は 50 ms にしました。

### 何が起きるか

1. 線の上の全員に一斉に問い合わせる要求はありません。複数の基板が同じ ID で違う中身を同時に送ると、衝突するからです（C-83、C-36）。
2. MD は指令が来ていなくても FB を送るので、聞くだけでどの ch がいるかが分かります。FB の DLC と bit 1、2 で、測れるものも分かります。
3. どの ch が同じ基板かは、設定で調べます。ch 0 から項目 4（受け持つ範囲）を読みます。応答があれば、その基板の範囲の次の ch へ飛びます。応答が無ければ次の ch へ進みます。応答が無いのは、その ch を受け持つ基板がいないか、要求が捨てられたかです。
4. 見つけた基板ごとに、項目 0（固有 ID）、項目 1（基板の種類）、項目 3（プロトコルの版）を読みます。
5. サーボには FB が無いので、台帳の決まりでは、サーボ宛ての設定（`0x410`）で同じ手順を踏みます。ただし今の CAN-Servo-v1 は答えません（「今の実装」）。

## 9. バスオフから戻ったとき

例の条件: MD の条件で、5 rad/s で回っています。アプリは `can.onFault(...)` を登録してあります。時刻 5 で基板の CAN がバスオフになり、20 ms 後（25）に自動復帰しました。

### 何が起きるか

1. 基板の CAN のコントローラが、エラーが重なってバスオフになります。バスオフは、エラーを出しすぎたコントローラが自分から線を離れる状態です。その間、線に何も出せず、何も受けられません。
2. マイコンの標準の自動復帰で戻ります。戻ったら、ポートが異常の詳細の bit 2「バスオフから復帰した」を立てます。
3. FB の bit 0 が立ちます。主制御は異常の詳細を読み、立った bit をアプリに知らせます。
4. bit 2 は、主制御のライブラリは消しません。アプリが消すまで残り、FB の bit 0 も立ったままです。立った bit は主制御が 1 を書いて消すまで残る決まりです（C-100）。その間、主制御は異常の詳細を読み直し続けます。
5. バスオフの間に指令が 100 ms 届かなければ、その ch は途絶で止まります（3 節）。この例は 20 ms なので止まりません。
6. バスオフの仕組みが無い実装（can2040）の基板は、bit 2 を立てません（C-68）。

### 線の上

### 今の実装

基板:

- バスオフの見張りはポートの仕事です。復帰に気づいたら `mas_can_node_raise_fault(node, MAS_CAN_FAULT_BUS_OFF)` を呼びます。node は異常の詳細に足し、FB の bit 0 を立てます（`send_fb`）。

| ファーム | バスオフ |
|---|---|
| `firmware/micro-MD` | `watch_bus_off` が、バスオフの flag が消えたら bit 2 を立てる |
| `firmware/CAN_MD` | 自動復帰を有効にしている（`Core/Src/main.c` の `AutoBusOff`）。bit 2 を立てる処理は無い（C-68 どおりではない） |
| `firmware/CAN-Servo-v1`、`examples/node_md_rp2040` | can2040 なので立てない |

- ポートが送れない間、node が積んだフレームは待ち行列（8 本）に残り、戻った直後に出ます。溢れた分は捨てます。FB だけでなく設定の応答なども捨てられます（案内の [node の関数と欄](../guide/board/node.md) の「気をつけること」）。

主制御:

- `Host::handleMdFeedback` が FB の bit 0 を見て項目 5 を読みます。`Host::handleSettingResponse` が、前に読んだときから新しく立った bit を `onFault` で知らせ、`w.faultDetail()` に残します。bit 0 以外は消しません。
- FB の bit 0 が立っている間、最後に読んでから 100 ms 経った後の最初の FB で読み直します（この例では 140 ms）。台帳 API-66 の言い方は「100 ms ごと」です。
- `w.clearFault()` は、`faultDetail()` に残っている bit に 1 を書きます。
- 主制御の側のバスオフ: `Esp32Twai::send` がバスオフを見たら復帰を始め、その送信は失敗にします（次の `update()` で送り直す）。`Host` はバスオフを数えず、`can.error()` にも残しません。RP2040 の `Rp2040Can2040` は can2040 なので、バスオフの仕組みがありません。
